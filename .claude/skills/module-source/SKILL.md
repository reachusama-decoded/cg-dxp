# Module source

Stage 1 of the seven, and the first three steps of the development flow (user, 2026-10-15):

**handbook → lesson plan → overview** → demo (`module-demo`) → challenges (`module-challenge`)

Each step is written from the one before it. The handbook is the source of truth for concepts, names, numbers and order; the lesson-plan block teaches from it; the overview is written from the lesson plan. Definition of done: `reference/subtask-descriptions.md` → **Source content**. Allowance: about one developer day including figures.

**Build order** (user, 2026-10-26). Stages A and B run first for every module of the session, in parallel, until the user has approved every handbook. Stages C and D are written after that gate, together with `module-demo` and `module-challenge`, for all the modules at once. The Asana stage keeps its wording (`reference/subtask-descriptions.md`, unchanged): its lesson-plan and overview items are completed in that later pass. The session's definition of done is `module-builder/references/session-checklist.md`.

## Before you start

1. Read `programme-profile` (SKILL.md, `references/layout.md`, `references/structure.md`, `references/conventions.md`) and this session's digest plus neighbours.
2. Read the module's brief in `designer/core/transcripts/cg-design-core.md` at the line structure.md gives, and the matching transcript passage in `cg-design-transcript-core.md`. The key questions and proposed challenge are the scope; TODOs are open, not agreed.
3. Read `courseware-conventions` (SKILL.md, `references/tone-of-voice-guidelines.txt`, `writing-rules.md`, `pedagogy.md`, `diagrams.md`) and `lesson-build` with `references/markdown-conventions.md`.
4. Read the handbook style model, `reference/L6-source content/M09 … Handbook (WIP).md` (structure, captions, further reading), and the session shape model, AIA `Unit 3: Building ML and AI Products/Session 12/` (its lesson plan, demo and challenge anchors).
5. Read the previous module's handbook (and, for a session's first module, the previous session's last artefact) for continuity: the artefact Jordan has, what learners can already do, the bridge out you must pick up.
6. Read [references/source-workflow.md](references/source-workflow.md) for the reference-led drafting steps and the outcome rules (its notes on module lessons are superseded by this skill).
7. Read `module-builder/references/session-checklist.md`, parts A and C.

## Stage A — references and brief (present for approval)

A short Markdown note in the scratchpad, then the references folder:

- **The research sweep** (source process step 1, done here, before any drafting) into `reference/cg-core-research/dayNN/mN-<slug>/`: `deep-research-<date>.md`, `references.md` (every link with its URL, the date checked, what it is and what was taken from it, and a licence note for anything copied), `notes.md` organised by the brief's key questions and the outcomes served, `decoded/` with verbatim copies of Decoded-owned material only, `figures.md` listing the figures the handbook needs, later `draft.md`, the wide draft. Vendor docs and articles are linked and quoted (two sentences at most), never copied. Reuse before redevelop.
- **The thread:** what this module receives from the previous one (S01: Jordan's weekly fund report as it stands) and what it hands on.
- **Outcomes served**: which of the session's outcomes (`internal-programme-overview.md` §6) this module delivers and which challenge task evidences each. Never module-level outcomes; propose a change to the programme document instead.
- **Section list**: the handbook's sections in order, one line each with its worked example and figure (plain titles; the PDF numbers them).
- **Scope cut**: what the module leaves out, sized for simplicity (session checklist item 13), and where it goes. Topic knowledge stays in the handbook, in its main text or, if truly optional, its appendix; delivery detail goes to the lesson plan; the rest goes nowhere.
- **CG hooks**: which "at CG" question goes to Catalyst, and where the module compares tools or platforms, so they are written with pros and cons from the start (`programme-profile` CG rule 2). Anything that depends on CG is raised in Asana, never written in as a `::: blocked` callout or a CG-access note (`programme-profile` rule 3).
- **Open decisions** for the user: scout first, then ask once, in one batch (AskUserQuestion), each fork with the recommended option first and marked "(Recommended)"; then carry on without further check-ins.

## Stage B — the handbook

`learner/moduleNN-<slug>/dayNN_mN_handbook.md`, in the shape `lesson-build` gives. A self-contained concept text a learner can read on its own: the concepts in depth, with nothing said about when to read it (user, 2026-10-19).

- **H1 title with `{#dayNN-mN-handbook}`, plain headings** (user, 2026-10-15): no typed numbers in H2 or H3, because `scripts/pdf-filters/handbook-section-numbers.lua` numbers them when the PDF is built. Each H2 section closes with `### Optional further reading` drawn from `references.md`, each item `- **Type:** [*Title*](url) by Source — what it adds.` (the PDF shows the type and the web address, with the description indented beneath); the last section is `## Summary {#dayNN-mN-summary .unnumbered}`, followed only by the optional appendix (source process step 5) when the handbook has one. Prose never cites a figure or a section by number ("the chart below", not "Figure 1.2").
- **The opening and the persona card** (user, 2026-10-19): under the H1, the breadcrumb and the italic tagline, one intro paragraph says what the handbook covers ("This handbook covers …"); straight after it comes each handbook's own card: `nbkit.persona_card_pdf_md(rows)` gives "#### Persona card — Jordan Mensah" and the overview's grid table, with five fields in order. **Who**: Jordan Mensah (they/them) works with code and data at Harbourline Asset Management, an invented UK asset manager. **This module**: where Jordan's work stands as the module begins, true to what the handbook then shows. **What gets in the way**: the problem the module solves for Jordan. **By the end**: what the work becomes by the end of the module. **The examples**: Harbourline, its funds and every number are invented; every output shown comes from a real run with Python and pandas, never with a version number ("Python 3.13", "pandas 2.3"). Each cell a line or two in Decoded's plain voice, consistent with the overview's card and CG rule 2 (no tool's limitations as the problem); check every cell against the handbook's own text (S01: M2 takes the report from the terminal on Jordan's laptop to a Linux server; M3 from one script to a package with pinned requirements). Who Jordan is, the invented data and the real runs live in the card, never in the intro paragraph (`lesson-build` markdown conventions → Handbooks). The card's words count towards the word range. After the card comes the useful output the handbook starts from, if any, then `## What this handbook covers {#dayNN-mN-covers .unnumbered}`, a heading the PDF leaves unnumbered, with its bullet list.
- **The 🧭 anchor after the persona card** (user, 2026-10-27; `programme-profile/references/conventions.md` → "Every module opens with the 🧭 anchor"). Write the module's entry in the session's `dayNN_anchors.md` (one question from the learner's own work; What, Why, How, one to three short lines each) as part of the source content, then run `nbkit.py anchors --session <folder>`: it places the anchor after the handbook's persona card and at the top of the module's lesson-plan section (the overview carries none: the day-level anchor is retired; user, 2026-10-27). The persona card stays as it is.
- **Exemplar first.** Open from the useful output (the report, the running thing), use AI to understand it, then explore selected methods. Motivate before teaching comprehensively.
- **Worked examples on the demo data with Jordan**, every number and output pasted from a real run in the dev container image (the dev container, or a throwaway container from its image), never edited by hand, and re-run after any pin, data or code change; `.venv/bin/python` is for quick checks and tooling only, never for a quoted output. These are the numbers every later step quotes.
- **Connected prose** (user, 2026-10-15): paragraphs that each develop one idea over several sentences (usually three to six), with transitions between them; no runs of one- and two-sentence paragraphs. This overrides Decoded's short-paragraph rule for handbooks.
- **Be specific, define first** (user, 2026-10-27; `courseware-conventions` writing rules, Decoded-wide). A reference back names the file, the command and what it shows ("`python fund_report.py > report.txt` once, then `python fund_report.py | diff report.txt -`, silent while they match"), never "a check" or "a saved copy". Every term and method is named and defined in plain words at first use, before any shorthand for it (test-driven development (TDD) before "test-first"). Where tests appear, say which level each is (unit, integration, end-to-end smoke) and what each level is good for. Check the tagline, the persona card, the intro paragraph and the covers list first.
- **Keep it simple** (user, 2026-10-26; session checklist item 13). The fewest files, folders, services, accounts, commands and steps that still deliver the outcome. At every fork, ask "is this the simplest version that works?"
- **Connect to real use.** Where the module's skill matters beyond the laptop, say at concept level how it carries on into the team's real environments (S02 M6: one image on the laptop, in the pipeline, in staging and in production, with only settings, secrets, data, size and the front door changing).
- **No in-line references**: no links, citations or "(VS Code docs, …)" asides in the prose, lists or captions. Sources go only in the section's "Optional further reading" list; paraphrase documentation, never quote it (the `::: catalyst` box is the one quotation).
- **Figures**: Python-generated PNG preferred (`scripts/figures/dayNN/mN_<what>.py`, brand palette and Work Sans via `scripts/figures/brand.py`, output to `courseware/common/figures/dayNN/`), Mermaid for flows; introduced from the line above; the caption is the image description (`![Caption.](../../../../common/figures/dayNN/mN-<what>.png){width=90%}`) or, for Mermaid, `<!-- caption: "…" -->` straight after the closing fence, never an italic "*Figure N.k*" line; draw the analogy, not just the concept; eyeball every render. If the figure labels the analogy against the technical terms, the text does not repeat that mapping as a "The proper words" line; keep the line for a complex idea whose analogy the figure does not label.
- **Every key question in the brief is answered** in the handbook (concepts) or the challenge (hands-on).
- **CG context**: Harbourline, Jordan's task, the synthetic data, reporting and historical performance; applications, websites and APIs as well as pipelines. Never assume portfolio-manager readers.
- **Catalyst first** for anything "at CG": a `::: catalyst` box with `source=`. Catalyst is named only inside these boxes; the prose around them stands on its own (user, 2026-10-15). Unresolved → a question for CG's programme contact, recorded in the digest, never guessed.
- **Code blocks** are formatted with `.venv/bin/python scripts/format_code.py learner/moduleNN-<slug>/dayNN_mN_handbook.md` (blacken-docs) after every change; comments that would split a line go above the code (the formatter moves them).
- **Tools and alternatives** follow `programme-profile` CG rule 2: pros and cons and what each is good for, never a tool's limitations, comparison-table headings included ("Good for", "Trade-offs"; never "Limitations"); teach verification and accountability as good practice every change gets, not as a fix for a tool's flaws. No `<!-- sensitive: … -->` marker.
- **AI-assisted engineering**: S01 M1 teaches Copilot; later handbooks explain the module's AI-assisted move as a concept and list the *Working with Copilot* appendix under "Optional further reading" rather than re-teaching it or linking it in the prose.
- **Prompts in the Copilot box** (user, 2026-10-16; `programme-profile/references/conventions.md` → "The Copilot box"): every prompt the handbook shows a reader how to type (a `/explain` question, a five-part brief) is a `::: {.copilot title="…" where="Chat view" mode="…" model="…" attach="…"}` div around a ```` ```text ```` block, or for a shell command `::: {.copilot title="…" where="Terminal chat" model="Fast"}` with no mode (`lesson-build/references/markdown-conventions.md` → "Copilot prompts"), never a blockquote or a bare fenced block. `title` names the job; `where` is Chat view (questions, plans, jobs that change files; mode required), Inline chat (one change to the selected code; no mode) or Terminal chat (a shell command; no mode), and a div without it draws as Chat view with an audit warning; `mode` is Ask, Plan or Agent and `model` Fast, Reasoning or Auto, chosen as the handbook teaches (Ask to understand code, Plan for a bigger change, Agent to create or change files; Fast for quick edits and questions, Reasoning for multi-step work); `attach` is `#<file>`, `selection`, `#codebase`, `#terminalLastCommand` or `#terminalSelection` when the prompt needs context (several separated by spaces). The closing lines per surface and mode are in `programme-profile/references/conventions.md` → "The Copilot box". Prompt lines stay under about 90 characters so they don't wrap in the PDF: one line per part of a brief. The box's closing line says what to do with the answer, so the prose after it moves on.
- **Expert notes**: at most two `::: expert` boxes, each the thing the docs don't say.
- **Self-contained**: never mentions demos, challenges, the session, the agenda, setup, instructors or Asana; never links into `instructor/` or a challenge notebook; never promises a later module. It may build on concepts from earlier handbooks.
- **Draft wide, ship the selection**: draft in the research folder's `draft.md` (step 2), and ship 3,000 to 12,000 learner words, aiming for about 7,000; past 7,000 only for topic knowledge, never delivery detail (user, 2026-10-26; `audit.py`'s `HANDBOOK_WORDS`).
- **The source process, in order (user, 2026-10-26; never skipped or shortened):**
  1. **Collect first** (Stage A). Before drafting, run a thorough research sweep across vendor docs, articles, standards and good-practice guides, and relevant internal material (Catalyst, Decoded's AIA, Fundamentals, the GenAI reference course). Use a research agent with web search. Record every source in `references.md`: each link with its URL, the date checked, what it is and what was taken from it. Write `notes.md` organised by the brief's key questions and by the session outcomes the module serves. Write the sweep up as `deep-research-<date>.md` in the research folder: a gap table against the brief, proposed additions each sized for simplicity, the Catalyst rules that apply, further reading, and any errors it found in the current text.
  2. **Draft wide.** Write `draft.md` in the research folder, organised around the key questions and outcomes, with enough substance to review and select from (more than will ship).
  3. **Add the assets.** Add diagrams, screenshots and other supporting assets where they improve learning. A figure whose rows explain something lines its rows up with the thing it explains (each group of Dockerfile lines level with the part of the image it makes), in the same order as its neighbouring figures.
  4. **Get a pedagogical review.** Commission an independent review from a separate reviewer agent, not the author's self-check. It covers missing foundations, overload, sequencing, suitability for adult learners, simplicity, vagueness and define-first; `module-review` → "Pedagogical review of a handbook draft" is its brief. The author never writes it, and a self-check never stands in for it. Save it as `pedagogical-review.md` in the research folder.
  5. **Reduce and refine.** The handbook is the source of truth for the topic, so topic knowledge stays in it (it may run past 7,000 words to hold it) or, if truly optional, goes to an appendix. Only delivery detail (click paths, room logistics, what to run when) moves to the lesson plan, which tells instructors what to deliver and how (user, 2026-10-26). Record what moved where in `notes.md`. Cut what adds little. Improve unclear explanations and diagrams. The appendix is `## Going further with <topic> {#dayNN-mN-appendix .unnumbered}`, after the Summary. It opens by saying that nothing in it is needed for working through the module, its exercises or its outcomes (never naming the demo or challenge: the handbook stands alone), and holds lettered `{.unnumbered}` H3s with their own `### Further reading for the appendix {.unnumbered}`. S02: Module 6's multi-architecture images, more container networking, secrets in depth, the supply chain.
  6. **Prose pass.** Read each section aloud, merge short paragraphs into the idea they serve, add the transitions, and move every source out of the prose into further reading.
  7. **Check the links.** Every link in the handbook (further reading and appendix included) appears in `references.md`, and the session outcomes the module serves are named in `notes.md`.
  8. **Present for approval.** The user approves every handbook of the session before the lesson plan, overview, demo or challenge is built (user, 2026-10-26). Record the approval in the digest.

## Stage C — the module's part of the lesson plan

Written from the approved handbooks, after the gate, together with the demo and challenge for every module, in the format of the `lesson-plan` skill (user, 2026-10-16; read its SKILL.md and `references/format.md`):

- **The section row** `### Module N — <canonical title> {#dayNN-mN}` in the timeline, the programme overview's title word for word, then the generated 🧭 anchor (no **Module outcomes.**: outcomes appear once, in the intro; user, 2026-10-27) and a section summary (the outcomes it serves, the session questions it answers, what learners do and make, the bridge in from the previous module). No key questions in the section row or its rows: they go in the module's part of the Question bank.
- **Its rows**, in 2.5-minute steps (user, 2026-10-27): the demo's about 20 minutes as one Instructor-led demo row per demo `### ` heading, titled with it word for word, each with a note and a Say that open with its heading in bold; a Questioning row after the demo; the challenge's 20 to 25 in two rows with a Questioning row between them; the debrief's 5; the break's 5 to 10, whose Transition is the bridge into the next module. Each row has its Purpose, On screen (once the demo exists: the file by its path from the session folder, then the notebook section, visual or COPILOT box title, never a cell number), Instructor notes, Say, Transition and Assessment (two short parts, `Outcome N · evidence`, or —).
- **Its reference section** `## Module N reference`, short: what a finished challenge looks like (once the challenge exists), the likeliest stalls, the fallbacks (no network, no key, a service that won't start) and the facts to have ready; no points for each visual or demo walk-through, because the demo rows carry each beat.
- **Prompts the instructor pastes**: where a row quotes a prompt in full, it is a `::: copilot` div around a ```` ```text ```` block with the same title, settings and text as the anchor's 🤖 COPILOT box; usually the row names the box instead ("the COPILOT box 'Turn the notebook into a script'").
- The module's lines in the Objectives table and the question-mapping sentence (the lesson plan is the only place that mapping lives), its key questions and two or three check questions in the Question bank, and its Support and stretch.
- **Pre-runs.** A demo step too slow for its row (a push, a pipeline run, a first image build or pull) is pre-run in the break before the module. The break row's notes and the checklist say what to run, and the demo row's note says it ran in the break.
- **Evidence.** In the Objectives table, a clause of an outcome that is evidenced only in the demo or debrief says so in its Evidence cell; core clauses are evidenced at Q1 or Q2.
- **Specific and defined.** Notes and Say lines name the file and the command, and define each term at first use before any shorthand (`lesson-plan` → Writing it well).
- The welcome's *What you will be able to do* row says which self-check question paces which module and what to adjust on a mostly-yes or mostly-no room; when a module is built, add or check its line. The plan may name modules; it never names an individual. The handbook may be named only as a whole, never by section.

`learner/module00-overview/dayNN_overview.md`, written from the lesson plan after the handbook gate, in learner order: first a one- or two-sentence opening that introduces Jordan before anything refers to them ("Every session follows **Jordan Mensah**, who … Here's where Jordan stands as this session begins."), then the persona card, then what the session is, tied to Jordan's report (and the artefact it builds on module by module), in connected paragraphs with no in-line links or citations (user, 2026-10-19: introduce the persona, then connect it to the session), Jordan's situation adapted to the session (`lesson-build` markdown conventions → Overview; the tier table's labels are marked `[Q1 · CORE]{.tier .core}`, `[Q2 · STRETCH]{.tier .stretch}` and `[Q3 · BONUS]{.tier .bonus}` so the PDF draws the notebooks' badges. "The questions you'll answer", with the `::: session` box, comes straight before the outcomes (user, 2026-10-19: the questions say what the session explores, the outcomes what you'll be able to show, so they read as a pair), never isolated at the end. No outcome, question or self-check item carries a trailing module tag ("*(Module 1)*", "(M2)"); the lead-in may say that each module answers some of the questions (user, 2026-10-15). **Outcomes, word for word (user, 2026-10-16).** The outcomes are `internal-programme-overview.md` section 6's, word for word: the overview's bullets and the lesson plan's Objectives table copy the session's outcomes table there exactly, bold verbs included, and never reword, shorten or reorder them. A change to an outcome is made in all of them in the same edit: `internal-programme-overview.md`, `dayNN_overview.md`, `dayNN_lesson_plan.md` and any partial quote of it in the handbooks, the demo, the challenge and the completed challenge. `module-audit` reports any that differ.

## Ship

Run the `lesson-build` checks (pandoc parse of the three files, `format_code.py --check`, `module-audit` to 0 errors and 0 warnings) and the session checklist's part A for this module. Hand the handbook's concepts, names and numbers (the worked examples' real values), its figures (the demo reuses them as concept cards where they fit) and the lesson-plan block's bridges to `module-demo` and `module-challenge`; they quote the names and values verbatim, never the handbook's section titles or numbers. Record scope cuts and decisions in the session digest.

**Concrete promises (user, 2026-11-02).** Never promise that learners can "trust" or "defend" something; say what they do that earns it (tested, scheduled, safe to rerun; checked against the source data; reviewed and checked on every push; presented, with questions answered). The exact technical senses stay (SSH host keys, checking Copilot's output).

**Action-first prose (user, 2026-11-02).** Summaries, purposes, section summaries, slide lines, cards and speaker notes say what learners do, in order, with a concrete object ("Write pytest tests for the report's code, fix it test-first…"), never a topic summary ("Make a change the way a team does", "An AI service that answers with evidence"). The rule and its banned words are in `courseware-conventions/references/writing-rules.md` → Learner-facing descriptions; reviews flag any line a reader couldn't picture doing at their laptop.

**Technical terms and completeness (user, 2026-11-02).** A summary names the techniques in the field's terms (FastAPI, RAG, agents, evals, dbt, Airflow), explained at first use or in the notes, and covers every module it summarises; check it against the module list ("Build a FastAPI service with model calls, RAG, agents and evals", not "Serve a JSON API whose AI summaries cite sources"). Rule: `courseware-conventions/references/writing-rules.md` → Learner-facing descriptions.
