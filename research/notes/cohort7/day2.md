## Whiteboard scripts

**STTM:** sources A and B joined into target T; the core of the artifact is the transformation rules. Textbook rule types: direct, constant, lookup (third table), aggregate (mean), derive/transform (concatenate as a subtype). Catalyst returns a CG-specific taxonomy with derive split further. The design documentation set: PRD, data contract, glossary/data dictionary, STTM, SLAs.

**SLI / SLO / SLA:** indicator = the measurable quantity (delay); objective = its ideal value (zero delay); agreement = the permissible departure (up to an hour late, beyond that you have broken the agreement). Indicators the room listed: delay from delivery time (which time zone?), latency, throughput, recovery time (service back, data restored, or back to an agreed level), delivery time, completeness/accuracy/freshness and other data quality measures, support measures such as a "duty to explain" (negative oil futures in 2020; the London barges story), availability. Nines: 90% ≈ 36 days a year ("a month"), 99% ≈ 3.65 days ("a working week"), 99.9% ≈ 8 hours ("a working day"), 99.99% ≈ 1 hour, 99.999% ≈ 5 minutes. Calibration: serious services offer three to four nines; Claude about one nine; AWS pays credits when it misses; the only thing that took AWS down for longer was a bombing. More nines = cloned infrastructure, global and local load balancers, 2% of traffic to the DR site to prove it works; the number of nines tells you about spare capacity.

**Paved path:** Databricks = compute that runs dbt; dbt = the transformation rules plus the data quality tests ("you write your STTM in dbt and tests for your quality"); S3 = storage, a cloud file system holding Delta files; Airflow = orchestration = timing and triggering of dbt runs; Astronomer = managed Airflow (CG ran its own; the paved path vends per-team Astro so teams stop queuing on a central platform); Docker = containers for development and deployment; Git/GitHub = version control whose PR events trigger release through Harness; Catalyst. Off the paved path is permitted with a real need (serving an API from S3, Dremio). Databricks-managed tables are not the paved path; S3-backed Delta is. Picture: a Morningstar CSV lands in S3 → dbt rules on Databricks, triggered by Airflow, copy it stage by stage until a consumer-aligned file exists.

**Data systems history (about 20 minutes):** data store/file system (1950s; no common structure, so the query layer must know every file) → database (common structure) → relational database (1970; relation = table = a set of tuples, unordered rows of ordered columns, hence primary keys) → ACID explained as linearizability (Alice writes 1, Bob 2, Eve 3; whatever fails or arrives out of order you read 1, 2, 3; logs make it possible) → non-relational databases (JSON, spreadsheets; pre-joined and faster by dropping linearizability; "the big-data decade was mostly wasted") → the internet (2000s) brings data bigger and faster than one disk → many machines → back to file systems in the cloud (S3) → Hadoop (HDFS plus a query approach, mid-2000s) → Spark (Databricks, 2014: faster, but the query layer still has to know the structure, which is why raw PySpark is complicated and not the paved path) → data lake = cloud file system plus query layer → lakehouse = a relational database split across S3 (files) and Databricks (compute), tabular with ACID back, done with Delta files whose logs and metadata track every write.

**Docker:** a container bundles the application with its dependencies down to the OS user space (not the kernel; a VM carries the OS and bypasses the host). Benefits: repeatable environments, isolation (one application per container, controlled ports — a port is an inbox owned by one application — and network), resource limits (CPU/RAM so a runaway container does not take the host down), Kubernetes to run many containers together. Dockerfile → image (template) → container (running instance). Dockerfile verbs: FROM (extend a base image; almost every Dockerfile starts with it), COPY, RUN, USER, EXPOSE, CMD/ENTRYPOINT. The dev container is a Docker container that VS Code launches into; the terminal prompt is inside it; tools like mise and astro are there; it is `edo-training-data-products`, based on the EDO data products base image, and EDO maintains it. "Mostly you write dbt files in the `data_products` folder of this container, run dbt from here, it creates tables on Databricks, and you commit from here."

**dbt and Airflow debrief (14:15):** dbt is ELT (seed/load first, transform in the warehouse); models are mostly SQL `select` statements with Jinja `{{ }}` replaced by SQL, and dbt turns each select into create table/insert; model name = file name; YAML files hold tests and materialisation (view vs table; an intermediate model is a table only if downstream consumers need it); OLTP (transactions, from retail ledgers; linearizability) vs OLAP (bulk insert and read; "a slow, annoying world"); commands `debug`, `seed` (CSV into Databricks, mainly for learning), `run`, `test`, `build`. Airflow: a DAG is a task collection (sequence, branches, fan-out) written in Python; at CG YAML blueprints fill placeholders in standard Python; the Databricks operator runs notebooks/jobs; the dbt task group (Cosmos) renders each dbt stage as an Airflow task. Learner findings: contracts translated to dbt "very straightforwardly"; one learner's product split into internal and external models with a union view, unprompted. Key message: if 80–90% of the technical job comes from the first pass over the contract, then interviews, transcripts, iteration and design review are the job; the remaining 20% is running, reviewing, testing edge cases. Michael's loop: transcribe → AI → print → hand-annotate → feed corrections back → iterate.
