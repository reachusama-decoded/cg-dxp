# Module self-review

Stage 4 of the seven: the refinement half of the 2-day module allowance. Definition of done: `reference/subtask-descriptions.md` → **Self-review**: you would be satisfied delivering this in a pilot; only then request peer review. It is the author's own pass: it never stands in for the independent pedagogical review of each handbook or the independent read-through of the session (session checklist items 4 and 24), which come from someone who didn't write the material (`module-review`).

## Before you start

1. Read `programme-profile` (SKILL.md, `references/layout.md`, `references/conventions.md`) and this session's digest.
2. Have the whole module open in the session folder: `learner/moduleNN-<slug>/dayNN_mN_handbook.md`, its block in `instructor/module00-overview/dayNN_lesson_plan.md`, `learner/module00-overview/dayNN_overview.md`, its section of the module demo notebook (`instructor/moduleNN-<slug>/dayNN_mN_demo.ipynb`) and the files beside it, its section of the module challenge notebook (`learner/moduleNN-<slug>/dayNN_mN_challenge.ipynb`) and its starter files, its figures in `courseware/common/figures/dayNN/`, its `references.md`. Have the previous module's material open too: this module builds on it.
3. Open `module-builder/references/session-checklist.md`: every pass walks its parts B to D.

## The method (MJB's; the method is flexible, the review is not)

1. **Read the full material carefully, in development-flow order**: handbook → lesson-plan block → overview → demo section (opening each file when the anchor says) → challenge section (each task box, the starting code and starter files it points at, then each reflect box and folded solution). Read once as a learner (handbook, overview, demo, challenge) and once as an instructor (lesson plan, following its beats into the handbook and the demo). Print it or read it in one sitting; do not skim a diff.
2. **Mark up or dictate corrections** into a single correction transcript in the scratchpad (`dayNN-mN-selfreview-pass1.md`): file, location, what is wrong, what it should say. Capture everything; batch, do not fix as you read.
3. **Apply the corrections** with an AI tool, at the earliest flow step each one touches, then mirror downstream. Tick each applied item.
4. **Read the updated version again.** One or two full passes; stop when a pass finds only cosmetics.

## The checklist (every pass)

- [ ] Every key question in the brief is answered in the handbook (concepts) or the challenge (hands-on), and the overview's questions match.
- [ ] The overview's outcomes match `internal-programme-overview.md` §6 verbatim, with no module tags on outcomes, questions or self-check items (at most three self-check questions, one per module, and the lesson plan's welcome says which paces which module); the lesson-plan block names the outcomes this module serves and maps the questions to it; each outcome is observable; each clause is evidenced in a challenge task, its core at Q1 or Q2, and a clause evidenced only in the demo or debrief is said so in the lesson plan.
- [ ] The module is about an hour in the pattern demo about 20, challenge 20 to 25, debrief 5, break 5 to 10 (lesson-plan skill); every `### ` heading of the demo's module section is exactly one lesson-plan row, with the same title and in the same order, nothing skipped or grouped; the closing ("Where the report goes next") is the last lines of the final beat, before CHALLENGE TIME, not a heading; the module's section title in the plan equals the demo's `## Module N — …` heading; the challenge rows name the challenge's `## … challenge — …` title and its Q1, Q2 and Q3 task titles exactly; rows of 2.5 to 20 minutes in 2.5-minute steps, start times h:mm (or h:mm:ss on a half minute); the audit fails on drift (user, 2026-10-27). Each demo row fits its minutes on a real run, with slow steps pre-run in the break and said so; paired challenges run in parallel and swap only for the review.
- [ ] **Connected**: the lesson plan's section summary picks up the previous module's artefact and its Break row's Transition leads into the next module; each module section opens with its 🧭 anchor and a bridge that names what it builds on (project, numbers, repository); the artefact grows from the previous module's.
- [ ] **Flow-consistent**: names, numbers and order in the lesson plan, overview, demo and challenge trace to the handbook; nothing downstream contradicts it.
- [ ] The handbook is self-contained: no demos, challenges, session, agenda, setup, instructors or Asana; no promise of a later module; the intro paragraph, then the persona card, then `## What this handbook covers {#dayNN-mN-covers .unnumbered}`; plain headings with no typed numbers (the PDF numbers them), every figure captioned by its description or a Mermaid caption comment, no "Figure N" or "section N" in the prose, further reading after each section, each item `- **Type:** [*Title*](url) by Source — what it adds.`, Summary `{.unnumbered}` (followed only by an optional appendix), the 🧭 anchor straight after the persona card, Catalyst only inside `::: catalyst` boxes.
- [ ] The handbook appears in the demo and challenge only in one Go deeper box at the end of each module section (fixed spelling, no path, link, section title or number, never when to read it); never in beat titles, bullets, code comments, alt text, cards or the files beside the anchors. The lesson plan and overview name "the Module N handbook" at most, never a section.
- [ ] Learner text never names a later module or session as where something is taught; the lesson plan may.
- [ ] The demo anchor runs top to bottom on a fresh kernel; every file it opens runs as it says; each challenge cell and starter file fails or misleads exactly where its task says; each folded solution's change, applied to fresh starter files, passes its check; the whole challenge runs on a fresh kernel without the demo having run; every quoted number and output matches a real run in the dev container image, and no output shows a warning.
- [ ] **The way of working** (`programme-profile/references/conventions.md` → "Learners direct AI and review what it wrote"): every challenge task has the learner prompt Copilot to write, fix or change the code (maths included), review what it wrote and run a check, never type code; `___` only records an observation or decision; folded solutions show a model prompt (in the Copilot box's badges and text block), the change and the check; the demo's AI-assisted beat models the same moves, its prompt in a 🤖 COPILOT box. Light maths, planted faults rather than gaps, Q3 not expected.
- [ ] **The box set**: the challenge uses AIA's boxes from `nbkit` (difficulty legend; a ⚡ Q1, Q2 and Q3 task box per section, Q1 first; ⌨️ terminal; 💭 reflect before every folded solution; 🎯 your turn; 📚 Go deeper last); the demo ends each module section with its 🏆 CHALLENGE TIME box, naming the same tiers and minutes, then its Go deeper box. The challenge is self-contained: its own setup cell, data path and starter files, nothing from the demo but the session's SSH remote.
- [ ] **The Copilot box** (`programme-profile/references/conventions.md` → "The Copilot box"): every prompt learners or instructors are given, in every file, sits in the standard 🤖 COPILOT box: `nbkit.copilot_prompt` in the anchors, with `nbkit.copilot_legend()` once in "How to use this notebook"; `nbkit.copilot_solution` (badges and a text block) in every folded solution; a `::: copilot` div with title, where, mode (Chat view only) and model in the handbook, lesson plan and overview. No prompt in a blockquote, a bare fenced block or behind a prose label such as "(Copilot Chat, Ask mode)". The surface fits the job (Terminal chat for a shell command, Inline chat for one change to selected code, Chat view otherwise), its closing line is that surface's (Inline chat: Keep or Undo; Terminal chat: Insert, not Run), shortcuts give the Mac key in words (Ctrl+I (Cmd+I on a Mac)), and the settings fit it too (Ask to understand, Plan for a bigger change, Agent to create or change files; Fast for quick edits and questions, Reasoning for multi-step work; ATTACH where the prompt needs context), and no prompt line runs past about 90 characters.
- [ ] CG context present: Harbourline, Jordan's beat (they/them), the synthetic datasets (demo data for the demo, challenge data for the challenge), reporting and historical performance, application or API examples.
- [ ] Every "at CG" answer comes from Catalyst with `source=`; unresolved ones are recorded in the digest, not guessed.
- [ ] Tools, platforms and ways of working follow `programme-profile` CG rule 2: compared with their pros and cons and what each is good for, in table headings and FAQs too, never framed by their limitations or weaknesses; review and checks taught as good practice every change gets, not as a fix for a tool's flaws; no `<!-- sensitive: … -->` marker.
- [ ] Everything runs on the dev container and the local services, and no file carries a CG-access note ("Needs CG access", `::: blocked`, "until CG answers", a mirror-container fallback, Asana, "the CG dev container"); `programme-profile` rule 3.
- [ ] No placeholder sections for modules not yet built; files beside the anchors carry the module prefix or sit in a named folder.
- [ ] **Simple, specific, defined**: the simplest version that works at every fork (fewest files, folders, accounts, commands, steps); every reference back names the file, command and what it shows; every term defined before its shorthand, in each file on its own; testing levels named where tests appear.
- [ ] Each module that works on a project has its own starting folder; the challenge's faults are not the demo's; Put it together starts from a state that Q1 and Q2 reach.
- [ ] Every config file the demo opens (a Dockerfile, a pipeline) has its line-by-line table; every figure that pairs two things lines them up row by row.
- [ ] Pins match `courseware/.devcontainer/requirements.txt` everywhere; each service has its README, INSTRUCTOR.md, test in `scripts/` and dev-container check, and its ports in the registry.
- [ ] Every 🧭 anchor in `dayNN_anchors.md` reads well: a question from the learner's own work, a What that names and defines, a Why from the team's work first, then Jordan's report, a How that says what happens, one clear sentence of at most 30 words each (user, 2026-10-27: 12-word phrases stopped making sense), nothing vague. The copies are generated (`scripts/nbkit.py anchors --check` passes).
- [ ] Handbook and overview prose reads as connected text: paragraphs of several sentences that develop one idea, transitions between them, no runs of one- and two-sentence paragraphs; no in-line links, citations or source asides (sources only in each section's "Optional further reading"); documentation paraphrased, not quoted.
- [ ] No "The proper words" line repeats a mapping its figure or diagram already labels.
- [ ] The demo section is visual-first (heading, anchor, bridge, module map, then one visual and three to five bullets per beat, code only where a beat runs something); each challenge section shows one recap visual after its anchor and bridge, before its first task box.
- [ ] Conventions match `lesson-build/references/markdown-conventions.md`; voice matches the tone-of-voice master: plain sentences, plain-English first use, no hedging or jargon, UK English.
- [ ] "Challenge" everywhere ("practice" retired from names, paths and timings); data from `../../../../common/data/demo` and `../../../../common/data/challenge` in the module notebooks; session files `dayNN_`-prefixed; no zip mentioned ("the course folder").
- [ ] Code formatted: `.venv/bin/python scripts/format_code.py --check` passes on the session folder; no line split because of a comment (comments that would split one sit above the code).
- [ ] No `TODO`/`TBC` in learner-facing text, no absolute paths, no keys, no individual names, no litter.

## Finish

Run `module-audit` on the session folder until it reports 0 errors and 0 warnings, then the rest of the checklist's part E (`scripts/check-session.sh dayNN`). Then hand the session to the independent read-through (`module-review` → Session read-through). Write a five-line summary at the top of the correction transcript (passes done, what changed most, what you are unsure about) and hand it to the peer reviewer with the module. Record any decision that constrains other modules in the session digest.

**Action-first prose (user, 2026-11-02).** Summaries, purposes, section summaries, slide lines, cards and speaker notes say what learners do, in order, with a concrete object ("Write pytest tests for the report's code, fix it test-first…"), never a topic summary ("Make a change the way a team does", "An AI service that answers with evidence"). The rule and its banned words are in `courseware-conventions/references/writing-rules.md` → Learner-facing descriptions; reviews flag any line a reader couldn't picture doing at their laptop.

**Technical terms and completeness (user, 2026-11-02).** A summary names the techniques in the field's terms (FastAPI, RAG, agents, evals, dbt, Airflow), explained at first use or in the notes, and covers every module it summarises; check it against the module list ("Build a FastAPI service with model calls, RAG, agents and evals", not "Serve a JSON API whose AI summaries cite sources").
