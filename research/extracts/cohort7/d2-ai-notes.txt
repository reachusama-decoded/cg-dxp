Data-product design and contracts
Source-to-target mapping STTM
• An STTM describes how data from source tables becomes data in a target
  table. It identifies the sources and target and, most importantly, specifies the
  transformation rules.

• Example: sources A and B are joined to create target T; a rule can specify
  whether a source column such as A1 is copied directly into a target column or
  transformed.
• Textbook transformation categories discussed:
  ◦ Direct: Copy a source column directly to the target.
  ◦ Constant-based: Populate a target value with a constant.
  ◦ Lookup: Find a value in another table.
  ◦ Aggregate: Calculate a value such as a mean.
  ◦ Derive/transform: Apply an operation to source data; concatenation may be
    treated as a subtype.
• Catalyst may use a product-specific taxonomy, with derived transformations
  split into more detailed categories.
• English-language rules need enough precision to resolve ambiguity, especially
  around edge cases and column-specific meanings of nulls, zeroes, and
  minimum or maximum values.
• A design document should clarify such rules before implementation.

        Service-level concepts
        SLI, SLO, and SLA
        • SLI Service Level Indicator): A measurable indicator of service or data-
          product performance.
        • SLO Service Level Objective): The desired target for an indicator.
        • SLA Service Level Agreement): The agreed permissible departure from an
          objective and the consequences or commitments associated with breaching it.
        • Examples of indicators discussed:
          ◦ Latency, throughput, and recovery time.
          ◦ Availability and delivery delay.
          ◦ Data completeness, accuracy, freshness, and other data-quality measures.
          ◦ Support response or turnaround time, including a possible duty to explain
            anomalous data.
        • Objectives should be clearly defined. For example, measuring delay relative to
          a delivery time avoids treating a delivery that is only marginally late as
          categorically different without specifying a tolerance. Time zone and other
          delivery-time details may also matter.
        • Recovery may mean restoring a service, restoring data, or returning service to
          an agreed level.
        Availability and resilience
        • Availability is commonly expressed as a percentage of time or in “nines. The
          lecture used these rough annual downtime approximations:
          ◦ 90% availability: about 36 days.
          ◦ 99%: about 3.65 days.
          ◦ 99.9%: about 8 hours.
          ◦ 99.99%: about 1 hour.
          ◦ 99.999%: about 5 minutes.
        • These are approximate illustrations; exact downtime depends on the




          measurement period.

Docker and development environments
Containers and images
• Docker packages an application and many of its dependencies into a container
  to support repeatable environments.

• A Dockerfile defines how to build a Docker image; an image is a template used
  to create containers. Dockerfiles commonly begin with FROM to extend a base
  image.
• Dockerfile instructions discussed included:

  ◦ COPY to place files in the image.

  ◦ RUN to execute build-time commands.

  ◦ USER to select the user.

  ◦ EXPOSE to document a port.

  ◦ CMD or ENTRYPOINT to configure what runs when a container starts.
• Containers generally share the host operating-system kernel rather than
  bundling a complete operating system as a virtual machine does. The lecture
  contrasted this with virtual machines, which provide a separate operating-
  system environment.
• Containers can isolate applications and control their network access, ports,
  and resource use, including CPU and RAM. Resource limits can prevent a faulty
  or overloaded application from consuming all resources on a shared host.
• Kubernetes can manage multiple containers and their interactions across a
  system.

        The paved path and its technologies
        Roles of the main components
        • The paved path is the recommended standardized technology set for creating
          discoverable data products. A specific use case may justify going off the paved
          path.
        • Amazon S3 Cloud object/file storage for the underlying data.
        • Databricks: Compute that runs transformations against the stored data.
        • dbt: SQL-based transformation and testing layer.
        • Airflow: Workflow orchestration, including scheduling and triggering dbt work.
        • Astronomer: Managed Airflow service, reducing the need for teams to operate
          Airflow infrastructure themselves.
        • Docker: Packages and runs the development environment and its
          dependencies.
        • Git and GitHub: Version-control code; code changes and pull requests can
          trigger release and deployment processes.
        • Catalyst: Supports the data-product workflow, including generating or




          assisting with artefacts.

dbt and Airflow
dbt
• dbt was described as an ELT tool: data is loaded first, and transformations are
  then performed in the data platform.

• dbt projects primarily use SQL, with Jinja-style templates such as {{ ... }}
  that are rendered into SQL.
• A dbt SQL file defines a model, which may materialize as a table, view, or
  another configured form. The file name typically determines the model name.

• dbt executes transformations that create or update the resulting relations;
  developers often write SELECT queries that define the model rather than hand-
  writing all the resulting table-creation and insertion operations.
• YAML files can configure models and tests, including materialization choices
  such as tables or views. Whether an intermediate model should be a table or a
  view depends partly on downstream consumers.

        Airflow
        • Airflow workflows are expressed as DAGs—directed acyclic graphs of tasks—
          with dependencies, branches, or parallel work.
        • Airflow tasks are commonly written in Python. The lecture also mentioned
          YAML-based blueprints as a way to populate standard task templates.
        • Databricks operators can run Databricks work. A dbt task group can represent
          dbt project stages as Airflow tasks.
        • Airflow handles the timing and triggering of work, such as running dbt on a
          schedule or in response to an event.

        Data systems: concepts and lecture framing
        Data stores, databases, and relational data
        • A data store or file system can hold files without requiring them to share a
          common schema. This makes the querying layer responsible for understanding
          each file s structure.
        • A database provides more structure. A relational database organizes data into
          tables (relations).
        • The lecture described a relation mathematically as a set of tuples: rows are
          unordered, while the values within a row have defined columns.
        • ACID properties were discussed: atomicity, consistency, isolation, and
          durability. The lecture connected transactions to reliable operations such as
          debiting one account and crediting another as a single unit.
        • OLTP systems focus on transactional operations and consistency; OLAP
          systems focus on analysis and bulk reading or transformation. dbt was
          discussed in the context of ELT and analytical workloads.
        • The lecture s historical account of non-relational systems and distributed data
          technologies was a simplified teaching narrative, not a comprehensive
          evaluation of those systems.
