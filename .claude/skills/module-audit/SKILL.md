# Module audit

The mechanical sweep. Where `module-review` asks "is it true and teachable?", the audit asks "does it match the pattern?". Fix issues at the earliest development-flow step they touch (handbook → lesson plan → overview → demo → challenges) and in the builder script if one exists.

## Run

```bash
.venv/bin/python scripts/audit.py courseware/<unit>/dayNN-<slug>/ [--strict] [--json]
.venv/bin/python scripts/audit.py --self-test   # the regression cases, after changing the audit
```

- The script is tracked in the repo at `scripts/audit.py` (moved from this skill's `scripts/` on 2026-10-19 so every developer's clone has it), beside `scripts/nbkit.py`, which it imports; it needs nothing from `.claude/`. The one skill doc it compares, the Activity types table in `lesson-plan/references/format.md`, is copied into the script as `LP_ACTIVITY_TYPES`: `--self-test` checks the copy against the doc, and reports that comparison skipped ("skipped: .claude not present") on a clone without `.claude/`. A change to that table is made in both.

- Takes one session folder in the 2026-10-27 layout (`programme-profile/references/layout.md`: `learner/`, `instructor/`, `dayNN_anchors.md` at the root; figures in `courseware/common/figures/<session>/`) and reports `file :: line N :: message` (`cell N` for notebooks) as errors (must fix) and warnings (inspect); exits non-zero on errors.
- **Target: 0 errors and 0 warnings** before anything is handed over (session checklist item 23). A warning judged a false positive is fixed in `scripts/audit.py`, with a self-test case, never left standing.
- `--strict` turns CG-access notes and unformatted files into errors: use it at stage 7 (delivery readiness), not before.
- Sensitive markers are retired (user, 2026-10-19): any `<!-- sensitive … -->` comment, cleared or not, is an error in every run, in Markdown, notebook cells (the notebooks beside the anchors included) and the files beside the anchors, with the message "sensitive markers are retired: reword to CG rule 2 (pros and cons, no limitations) and delete the marker". Reword the passage to `programme-profile` CG rule 2 and delete the marker. A name such as MJB or Michael is an error that says to use the role. Whether the wording itself is limitation-led is a judgement for the checklist, not the script.
- CG-access notes warn in every run (user, 2026-10-16): a `::: blocked` callout or `<!-- blocked: … -->` marker, a "Needs CG access" heading, the same note without one ("Needs CG access" as a label, "until CG answers", a mirror-container fallback, a check on a CG laptop, Asana), and the phrase "CG dev container" (in prose, notebook cells and the files beside the anchors), with the message "CG Core content never carries CG-access notes; the course runs on local containers". Remove the note; the rule is `programme-profile` rule 3.
- Run it with the project venv: the formatting check runs `scripts/format_code.py --check` on the session folder through the same interpreter, which must have isort, black and blacken-docs.
- `--self-test` runs the regression cases and exits: "practice" as a name, the lesson-plan cases (a passing lean plan, a module a little slower that still passes and Adapt last, then a failing case for each rule: a 25-minute row or one off the 2.5-minute steps, a start time off the half minute, a gap, a timeline that stops short, fields out of order, Key questions in a row or a section row, Say past two lines or one breath, notes past three bullets, a one-line field of two, a long section summary, a demo split into rows, a challenge in three rows, a 75-minute module, a debrief before the challenge, no break, a timed check-in in a challenge row, Put it together as its own block, a last block that isn't open challenge time, open challenge time with an Explain row or without Put it together named as optional, a start and end of 40 minutes, a retired reference part, four stalls, a module missing from the Question bank, plus the template parts, activity types, Assessment and outcome numbers, an Assessment in the old three parts, with no evidence or past 15 words, and an On screen that doesn't open on a file), each proved by mutation, the CG-access cases, eleven `challenge-solution/` cases (a clean one, then missing folder, missing file, not executed, error output, `___` left, a changed folded solution, a missing challenge cell, a cell of its own named `-solution` (clean) and one not so named, drifted task boxes), each on a throwaway session folder, the persona-card cases, the five handbook persona-card cases (user, 2026-10-19: a card straight after the intro paragraph passes, with no short-paragraph run from the breadcrumb and tagline above a one-sentence intro; a missing card, fields out of order, a version number in the card and a card after a section warn), the Copilot-box cases (a passing and a failing case for each rule: a box on each surface, no WHERE, a WHERE outside the vocabulary, MODE on Inline chat or Terminal chat, Chat view without MODE, no MODEL, badges out of order, two ATTACH badges, ATTACH with a comma or a misspelt terminal value, WHERE on the wrong colour, another surface's closing line, a folded solution's badge line, the legend's WHERE and terminal ATTACH rows, the legend once per anchor, `::: copilot` divs with and without a valid `where`, `mode`, `model` and `attach`, and a `then=` or a notebook box's own closing line that fits its surface or names a mode, Keep or Undo on Terminal chat, or Run or Insert on Inline chat; a sentence that opens with "Run" passes, a bold **Run** doesn't; Inline chat in a notebook cell: `nbkit.COPILOT_THEN_NOTEBOOK_CELL` or a line of its own naming **Accept and Run** passes, bold or not, a Chat view box carrying that line warns, and Accept and Run on Terminal chat, a bare Accept or Discard on Inline chat and "Accept, and Run" warn, while a bold **Accept** is left to the content-wording check so it is reported once), the handbook stand-alone cases (the H1, breadcrumb, code and heading ids pass; "Module N" in any case, "the previous / earlier / last / other module", "earlier / later in the session", another module's file, figure or handbook name, and another module's coined term (Module 1's "lab bench and recipe card", Module 2's "harbourline-remote" and Module 3's "asked for two, got seven" included) warn; a module's own files and terms, "earlier in the file", another session's handbook and "other modules" in a sentence about Python's modules pass) and the content-wording cases (Keep and Undo, "Cmd+I on a Mac", plain-English accept and discard, Source Control's Discard Changes and a code block pass; **Accept and Run**, bold or not, passes; a notebook cell reports each problem once; a notebook's markdown cell, a Markdown file beside an anchor, and a challenge anchor whose Inline chat box closes with the notebook-cell line (passes) or whose Chat view box carries it (warns), end to end).
- The outcome-wording cases run in `--self-test` too, each on a throwaway repo root holding a `internal-programme-overview.md`, an overview, a lesson plan and a challenge notebook: all matching passes (a short quote, an unrelated quote, a quote in code and HTML attributes are ignored); one word changed in the overview, one in the lesson plan, an outcome missing, an extra outcome, a stale partial quote (in the notebook, one that keeps only the start of the outcome's clause, and in a Say line) and the programme overview changed alone are errors, each the passing fixture with one mutation asserted to apply once; no table for the session, a missing overview or lesson plan and no `internal-programme-overview.md` warn (user, 2026-10-16).
- `--self-test` also runs the demo-row and challenge-row cases (user, 2026-10-27): one row per `### ` heading with the same title, in the same order, passes; a skipped, grouped, renamed or reordered heading, a module section title that differs from the demo's `## Module N` heading, the closing written as a heading, and a challenge row whose challenge title or Q1–Q3 task titles differ are errors; no demo anchor and rows still to write are skipped. The exact cases are the script's.
- `--self-test` also runs the eleven sensitive-marker cases (user, 2026-10-19): an open, a cleared, a spaced and an upper-case marker are errors, and so is a marker in a notebook cell, strict or not; a caption comment, the plain word "sensitive", a role and a notebook without a marker pass; an individual's name is an error that points to the role, never to a marker.
- `--self-test` also runs the table-of-contents cases (user, 2026-10-16): a challenge, a demo and a completed copy that pass, with a `## ` line in fenced code and one in a folded solution; a completed copy's own `-solution` cell and a marker line before a heading, which pass; one case per error above; end-to-end runs through `audit_notebook` (a notebook beside the anchors needs none) and `check_challenge_solution` (the copy of a challenge without a table is left to the challenge's error); and, when nbkit has `apply_toc`, notebooks it built pass while one changed after it fails as out of date.
- Programme-specific lists (allowed and retired callouts, banned words, unobservable verbs, session-reference phrases, the handbook word range, name patterns, and `COINED_TERMS`, each session's terms a module's handbook coins) are at the top of the script. When a handbook names an idea of its own that a later handbook might lean on, add it to `COINED_TERMS` under its session and module (S01: Module 1's "four moves", "five-part brief" and "lab bench and recipe card", its picture of notebook against script, a section title and a figure; the short "bench and card" is the lesson plan's, not the handbook's, so it is not listed; Module 2's "harbourline-remote", the training server it builds, and Module 3's "asked for two, got seven", its name for pip pulling in transitive dependencies). Only distinctive names go in, never ordinary technical words any handbook may use (venv, facade, strict mode, standard output).

## Planted-fault teaching files

Some files are broken on purpose: the demo's `mN_break_it.py`, which stops with a traceback learners read, and a challenge starter presented as a draft to review (`*_copilot.py`, S01: `challenge/m1_fund_report_copilot.py`, with a working-directory data path, a filter that drops rows and an `except` that hides errors). The audit recognises them **by file name only**, through `PLANTED_FAULTS` at the top of `audit.py` (`^m\d+_break_it\.py$`, `^(m\d+|together)_\w*_copilot\.py$`): the name says what the file is for in the story, never what is wrong with it, and nothing inside the file (no comment, marker or pragma) gives the fault away, so learners reading the file learn nothing from the exemption. For these files the working-directory path and error-handling checks are skipped; every other check still applies (keys, absolute paths, names, the handbook, self-containment, naming, formatting). The report lists each one as a `NOTE` line (and under `exempt` in `--json`), not counted as a finding, so a reviewer sees what was skipped. The planted faults themselves are listed for instructors in the lesson plan. A new kind of planted-fault file gets a name pattern added to `PLANTED_FAULTS` with a one-line reason, never an in-file marker.

## Keep the script honest

When a new mechanical rule is confirmed for Core, add it to `scripts/audit.py` with a one-line reason and test it on a synthetic fixture in the scratchpad before running it on content: a clean session that must report 0 errors and 0 warnings (every box from `nbkit` and a planted-fault file of each kind included), a Markdown-anchor variant, and a broken session that trips every rule, with a script that asserts each expected message. Box spellings live in `nbkit` only: the audit imports `nbkit.box_patterns()` from `scripts/nbkit.py` beside it, so a change to a box is made in `lesson-build/references/notebook-boxes.md` and `scripts/nbkit.py` (checked with `scripts/nbkit.py selftest`), never here.
