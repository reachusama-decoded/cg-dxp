# Module challenge

Stage 3 of the seven, and the last step of the development flow: handbook → lesson plan → overview → demo → **challenges**. The challenge section is written from the demo: it applies the demo's skill to its own question on the challenge data. It is the evidence of learning: outcomes are judged by what learners show in it. Definition of done: `reference/subtask-descriptions.md` → **Challenges**.

## The way of working: learners direct AI, then review what it wrote

Read `programme-profile/references/conventions.md` → "Learners direct AI and review what it wrote" before anything else. It is the pattern across the whole programme and the key difference from AIA's challenges: learners never write code or do maths by hand. They prompt Copilot to write, fix or change the code (any calculation included), review what it wrote, run it, and confirm from the output and a check whether it works, keeping or undoing the change. Every task box, code cell, starter file and folded solution below follows from that.

## Before you start

1. Read `programme-profile` (SKILL.md, `references/conventions.md`, `references/layout.md`, `references/structure.md` for the capstone demonstrations) and this session's digest.
2. Read the module's handbook, lesson-plan block and demo section: the challenge uses the handbook's names, practises what the demo showed (its AI-assisted beat included), and produces the evidence the lesson plan's "what a finished challenge looks like" will quote.
3. Read the previous module's challenge notebook (`learner/moduleNN-<slug>/dayNN_mN_challenge.ipynb`): the previous module's task and its artefact are what this task builds on.
4. Read the brief's proposed challenge for this module (structure.md line pointer) and the session digest's challenge design, if there is one (S01 M1: "Fix and review the report script").
5. Read [references/challenge-format.md](references/challenge-format.md) and `lesson-build/references/notebook-boxes.md` (the boxes' exact HTML and the `nbkit` helper for each); for Session 09, [references/capstone-format.md](references/capstone-format.md).
6. Look at AIA `Unit 3: Building ML and AI Products/Session 12/challenge/` for the look (boxes, tiers, reflect before solution), not for its gap-filling.
7. Read `courseware-conventions/references/pedagogy.md` → Challenges for ramping and reflect-before-solution only: its gapped tasks and "tiers off" do not apply to Core, whose way of working (above) overrides them.
8. Read `module-builder/references/session-checklist.md`, parts B to D: the rules every session is built against.

## What to build

In `courseware/<unit>/dayNN-<slug>/learner/moduleNN-<slug>/`:

- **The module's section of the anchor** (`dayNN_mN_challenge.ipynb`, or `dayNN_mN_challenge.md`), built through `nbkit` so every session matches: `## Module N — <task name>`, the 🧭 anchor, the bridge (what it builds on, concretely), one recap visual of the demo section it follows, then the tiers. Each tier is a ⚡ task box (`nbkit.task_box`), the starting code with its planted fault, a 🤖 COPILOT box (`nbkit.copilot_prompt`) wherever the task hands learners a prompt to use, ⌨️ terminal boxes before terminal steps (`nbkit.terminal_box`), and a 💭 REFLECT box with the folded solution (`nbkit.reflect_solution` around `nbkit.copilot_solution`). 🎯 YOUR TURN boxes (`nbkit.your_turn_box`) carry short tasks with no code. Last, the **Go deeper box** in its own markdown cell (`md(nbkit.go_deeper(N, body))`).
- **Starter files beside the anchor only where the task needs them** (a script to review, a config to fix): one file carries the module prefix (`m1_fund_report_copilot.py`), several go in a named folder. The anchor says when to open each and when to come back. A starter file with planted faults is named for what it is in the story (`*_copilot.py`: a first draft to review), never for its faults, and the text never credits its faults to Copilot (CG rule 2: no tool's limitations).
- **The put-it-together task** as the anchor's last section, written with the module challenges once the session's handbooks are approved, starting from a state that a learner who stopped at Q1 or Q2 of each module can reach, never from a Q3 result, and naming that state in its first lines (the files, the repository, the branch): the optional stretch for fast finishers, never a block everyone does (user, 2026-10-16). Learners reach it in the session's last block, open challenge time, once they've gone as far as they want with the module challenges; it has no fixed time and says it is optional. The same boxes and the same way of working, one task on the challenge data that needs all three modules' skills and ships the session's artefact (S01: Jordan's report, written, run remotely, packaged). Starter files, if any, use `together_` or `together/`.
- **The completed challenge, `instructor/moduleNN-<slug>/challenge-solution/`** (user, 2026-10-16; instructor side 2026-10-27), (`courseware/<unit>/dayNN-<slug>/instructor/moduleNN-<slug>/challenge-solution/`), one level deeper than the learner module folder, with the same file names as its challenge files, so its paths into `common/` go up one more level (five) (`../../../../../common/data/challenge`). It has the same file names as the learner module folder's challenge files (day01: `day01_m1_challenge.ipynb` and `m1_fund_report_copilot.py`), plus any file the tasks have learners make, and is the challenge done in full, for instructors to show a finished version in the debrief:
  - every task done with the model answer its folded solution gives, Q3 · BONUS and the put-it-together task included: the cells hold the fixed code, and the starter files are the fixed versions, under the same names;
  - the answer boxes filled (My reading, My review, My checks, the 🎯 YOUR TURN tables) with what the model answer saw and decided, so no `___` is left;
  - the notebook executed top to bottom with its outputs (the session's services started first), with no error output; the folded solutions, task boxes and everything else stay exactly as in the challenge.
  It is built after the challenge is verified, and rebuilt in the same pass whenever the challenge changes, so its task boxes always match. It never ships to learners: the build copies it to `release/latest/<unit>/<session>/instructor/challenge-solution/` (so it runs as it is) and prints it to `instructor/dayNN_mN_challenge_solution.pdf` in the same session folder (`scripts/notebook_pdf.py --with-files`); nothing under `learner/` links to it. Learner text never mentions it. The steps are in [references/challenge-format.md](references/challenge-format.md) → "The completed challenge".
- No placeholder sections for modules not yet built. If the anchor does not exist yet, create it with the title cell, the how-to-use cell (with `nbkit.difficulty_legend_html()` and the Copilot settings legend, `md(nbkit.copilot_legend())`, in that cell or the next), the setup cell and the footer, then run `scripts/nbkit.py toc --nb` on it for the 🗺️ table of contents; never type the table.

Rules that matter most:

- **AI writes the code; learners review it** (conventions.md). Task lines read "Ask Copilot to …; review …; run the check …". Code cells hold the starting code (complete, with its planted fault where there is one) for Copilot to work on; `___` gaps only record what the learner observed or decided (an error type, a line number, Keep or Undo and why), in markdown or a string. No `# TODO` for the learner to code, no "Step N" headings, no "fill the gaps".
- **Planted faults, not gaps.** The tasks centre on reading, reviewing and fixing Python with AI help: a traceback, Copilot `/explain`, reviewing a draft script, Keep or Undo, a recorded check. Each cell or starter file is complete code with a fault the learner finds by reading and running it, then has Copilot fix at their direction.
- **Every prompt in the Copilot box** (user, 2026-10-16; `programme-profile/references/conventions.md` → "The Copilot box"). Where a task hands learners a prompt (a `/explain` question, a first instruction to adapt), it sits in a 🤖 COPILOT box straight after the task box: `md(nbkit.copilot_prompt(title, prompt, mode, model, attach=None, purpose=None, then=None, where="Chat view"))`. Where the task is to write their own prompt (a five-part brief), the task box asks for it and names the settings to choose, and the model prompt appears only in the folded solution. Badges from the vocabulary only: WHERE Chat view, Inline chat or Terminal chat (Terminal chat for a shell command, Inline chat for one change to the selected code, Chat view otherwise; pass `mode=None` with the last two; an Inline chat box's purpose line says which lines to select, and its ATTACH never holds `selection`, which Inline chat works on already; Inline chat in a notebook cell keeps WHERE Inline chat but passes `then=nbkit.COPILOT_THEN_NOTEBOOK_CELL` or its own line naming **Accept and Run**, which applies the change and reruns the cell, because VS Code shows that button in a cell rather than Keep and Undo, and the task text says the same; a box for a `.py` file in the editor keeps the Keep or Undo default; a task that follows an Agent edit in the same file says to Keep or Undo it first, because Ctrl+I in a file with Chat view edits not yet kept or undone opens the Chat view instead), MODE Ask, Plan or Agent with Chat view only (Ask for `/explain` and questions, Plan for a bigger change, Agent for a job that changes files), MODEL Fast, Reasoning or Auto (Fast for quick edits and questions, Reasoning for multi-step work), ATTACH `#<file>`, `selection`, `#codebase`, `#terminalLastCommand` or `#terminalSelection` when the prompt needs context. Prompt lines under about 90 characters. The legend goes once in "How to use this notebook".
- **Light maths.** Any calculation is Copilot's to write and the learner's to check against a known number; no maths-heavy tiers.
- **Tiers, AIA style.** One ⚡ task box per tier: Q1 · CORE (green) for everyone, Q2 · STRETCH (orange), Q3 · BONUS (red) not expected and saying so. Every section opens its tasks with Q1. The header gives the title and Individual or Pairs, and no times anywhere in the challenge: the demo's 🏆 CHALLENGE TIME box gives the one fixed time for all three tiers (user, 2026-10-16); the body a bold one-line goal and "Task N.k —" lines (`nbkit.task_box` numbers them). **Go as far as you can** (user, 2026-10-16): no tier is mandatory and nobody is chased. Learners start at Q1 and stop where the time stops; Q1 fits the challenge time for most of the room, and Q2 and Q3 are there for whoever gets further. The notebook says so in "How to use this notebook", and task and answer boxes stay short.
- **Reflect, then the folded solution.** Every solution sits inside a `<details>` block straight after a 💭 REFLECT box (`nbkit.reflect_solution`), and shows a model prompt with its Copilot settings, the change a good answer makes (the fixed code) and the check that proves it (`nbkit.copilot_solution(prompt, change, check, mode=…, model=…, attach=…, where=…)`, which gives the prompt the 🤖 COPILOT box's badges and a ```` ```text ```` block; never a blockquote after "A prompt that works" or a prose label such as "(Copilot Chat, Agent mode)"), then the reflect answer. Several prompts in one solution go in one text block, a blank line between them. A challenge notebook ships without outputs.
- **Self-contained.** The challenge has its own setup, opened by the challenge data's card (`md(nbkit.data_card("the challenge data", rows))`, the same fields as the overview's card, Files row included), then a setup cell (imports, the path to `../../../../common/data/challenge`, a file check), its own starter files in `challenge/`, and never needs a demo cell, a demo file (S01: `m1_fund_report_reviewed.py`, `m1_break_it.py`), the demo anchor or a demo variable, so a learner who ran nothing in the demo can do it. Services started during setup (S01's SSH remote, `courseware/common/services/remote-machine/`, reached from `challenge/` at `../../../../common/services/remote-machine/`) are not demo content and may be used.
- **One recap visual after the anchor and bridge** (user, 2026-10-15; order 2026-10-27). Each section, the put-it-together task included, shows one visual that recaps the demo it follows, before its first task: the demo's module map or its key concept card reused from `courseware/common/figures/dayNN/`, or the demo's Mermaid flow. One visual, no new teaching; then the tasks.
- **The 🧭 anchor first, identical to the demo's** (user, 2026-10-27; `programme-profile/references/conventions.md` → "Every module opens with the 🧭 anchor"): heading cell · anchor cell (generated by `nbkit.py anchors`, also in `challenge-solution/`) · bridge cell ("This builds on …" plus one sentence into the recap map) · the recap map cell, then the section's existing cells. Put it together has its own anchor (`## together` in `dayNN_anchors.md`).
- **One task, the module's challenge time plus a 5-minute debrief, observable evidence.** A module's 75 minutes give the challenge 25 (user, 2026-11-02: 15 minutes of work, a 2.5-minute Questioning check-in, then 7.5 minutes of Learners keep working), followed by 15 minutes of Shareback/questions, where learners show what they made and ask, and the 5-minute debrief; the demo's 🏆 CHALLENGE TIME box says how long; the instructor stays available at the back of the room with no check-ins, and the debrief walks through the solution in `challenge-solution/` or asks questions that surface blockers. The tiers are one task's ramp; "what a finished challenge looks like" (in the lesson plan) is the standard of the session outcome(s) the module serves, made concrete, and the recorded check is its evidence. Each clause of each outcome the module serves has its evidence in a task, the core clauses at Q1 or Q2; a clause evidenced only in the demo or debrief is said so in the lesson plan's Objectives table.
- **Connected.** The task starts from the artefact the previous module's task left (or the story the demo told, for the first module) and says so in its bridge, naming the files, numbers and repository, without needing the demo's files.
- **One starting folder per module** (user, 2026-10-26). Where the task works on a project, `challenge/mN_<project>/` holds its start as the module begins, with the previous module's fixes in, so a learner who fell behind starts fresh. A folder or repository that a later task continues in is named once and called the same in every task, the completed challenge and the lesson plan (S02: `m5_fund_report/`, on Harness as `fund-report-challenge`).
- **Simple, specific, defined.** The fewest files, steps and accounts that still evidence the outcome (`programme-profile` CG rule 10). The challenge stands alone, so it defines every term at its first use, before any shorthand (S02 Module 4 defines fixture and test-driven development (TDD) in its anchor and first task), and every reference back names the file and command.
- **Demo ≠ challenge.** The challenge data (`../../../../common/data/challenge`), not the demo data: same schema and context, different funds, numbers and planted faults: no fault the demo fixes appears in the challenge, even in another form, so the skill transfers and the answers cannot be copied.
- **Prerequisite-honest**: everyone can finish Q1; an experienced learner moves on to Q2 and Q3; nobody is stranded.
- **Capstone-aligned** where the module's skill is one the capstone demands (JSON API, Docker, dbt, vendor GenAI API with checks).
- **Paired and discussion tasks** where they give better evidence (the task box header says Pairs), always with a solo route for one learner on a laptop. Partners work in parallel, each on their own laptop and copy, and swap only for the step that needs the other person (a review at the author's screen), so neither waits through the other's work (S02 Module 5). No chat, polls or breakout mechanics.
- **Local containers.** Runs on the challenge data in the dev container and the local services in `courseware/common/services/`; no CG-access note, `::: blocked` callout or CG-specific variant, and it's "the dev container", never "the CG dev container" (`programme-profile` rule 3; user, 2026-10-16).
- **The handbook appears only in the Go deeper box** (user, 2026-10-15): one per module section, at its end, in the fixed spelling, naming "the Module N handbook" with no path, link, section title or number. Task boxes, solutions, starter files, recap visuals and alt text never mention the handbook; the put-it-together section has no box.
- **Challenge, never practice.** The activity, its folder, its anchor and its data are "challenge"; the data is the challenge data at `../../../../common/data/challenge`.
- **Formatted code.** Run `.venv/bin/python scripts/format_code.py challenge/` after every code change and finish with `--check` passing; comments that would split a line go above the code (the formatter moves them). Solution code folded in a markdown `<details>` block is not reached by black, so write it in black's style. A planted fault is still formatted code: the fault is in what it does, not in how it is laid out.

## Verify

Play the learner with Copilot's part done by you: run each starting cell and starter file as shipped and confirm it fails or misleads exactly where the task says (and nowhere else); apply each folded solution's change to a fresh copy and run its check, in the dev container image; confirm every number the anchor or the lesson plan quotes. Run the whole challenge from a fresh kernel without having run the demo. Walk it as a struggling learner: where do they stall, and does the task box or the lesson plan's hint cover it? Does Q1 fit the challenge time for most of the room? Do paired steps run in parallel? Does Put it together start from what Q1 and Q2 leave? Clear the notebook's outputs. Then build or rebuild `challenge-solution/` from the verified run (references/challenge-format.md → "The completed challenge"), execute it in the dev container image and look at it as the instructor will show it. No output shows a warning, and every pin matches `courseware/.devcontainer/requirements.txt`. Then `module-audit` on the session folder (it warns when `challenge-solution/` is missing, not executed, has an error output or a `___` left, or its task boxes have drifted from the challenge's): planted-fault starter files are listed as notes and skip the path and error-handling checks, recognised by name only.

## Ship

The anchor section with its recap visual, boxes (every prompt in a 🤖 COPILOT box, the Copilot legend in "How to use this notebook"), starting code, starter files, folded solutions and closing Go deeper box in place, code formatted; the 🗺️ table of contents rebuilt with `scripts/nbkit.py toc --nb` in the challenge and the completed copy, the two tables identical; `challenge-solution/` rebuilt from this version of the challenge, executed with no error output and no `___` left, its task boxes matching the challenge's; the demo section's 🏆 CHALLENGE TIME box matching the tiers (`module-demo`); the lesson-plan block's two challenge rows (naming this section's `## … challenge — …` title and its Q1, Q2 and Q3 task titles exactly; the audit fails on drift; user, 2026-10-27), what a finished challenge looks like (a line per tier), the three likeliest stalls and the debrief filled in from the verified run, byte-identical where they quote the anchor. If a change alters the duration or the evidence, mirror it into the lesson plan and the overview's agenda in the same pass. Then the session checklist's part E: audit 0 errors and 0 warnings, `format_code.py --check`, both tables of contents `--check`, and the dev-container and service tests (`scripts/check-session.sh dayNN`).
