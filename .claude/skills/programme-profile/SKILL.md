## Programme map (working order, proposed to MJB 2026-10-13)

Nine half-day sessions: four taught units of two half-days each (six modules per unit, three per half-day) plus a capstone half-day. Module questions still come from the brief; the mapping from each module to its brief source is in [references/structure.md](references/structure.md). Questions and outcomes per session: `internal-programme-overview.md` §6.

## Module anatomy and timing (working — half-day timetable is TODO(MJB))

A module is one hour (user, 2026-10-15). Working split:

| Part | Working minutes | Artefact |
|---|---|---|
| Teach and demo | 20 | The module's handbook (concepts) + its section of the module demo notebook (`instructor/moduleNN-<slug>/dayNN_mN_demo.ipynb`); the lesson-plan block says what to teach from the handbook |
| Challenge | 25 | The module's section of the module challenge notebook (`learner/moduleNN-<slug>/dayNN_mN_challenge.ipynb`), starter files beside it only where needed, solutions folded |
| Debrief and bridge | 5 | The lesson plan's debrief row; the break row's transition is the bridge into the next module |
| Break | 10 | After every module |

**Session files (user, 2026-10-15; learner/ and instructor/ 2026-10-27).** Every session folder has the same shape, split by audience and then by module ([references/layout.md](references/layout.md); module folders `moduleNN-<slug>`, numbered unit-wide, with `module00-overview` for the day-level files and Put it together in its own folder after the last module, user, 2026-10-27; each module notebook self-contained with nbkit's short header): `learner/module00-overview/dayNN_overview.md` (learners, in this order: a Jordan opening, the persona card, the session, how the day runs, the questions, the outcomes, before you start, the agenda and how the challenges work, the data), `instructor/module00-overview/dayNN_lesson_plan.md` (instructors: Decoded's lesson plan template adapted for CG Core, built to Word; the `lesson-plan` skill), `learner/moduleNN-<slug>/dayNN_mN_handbook.md` (one self-contained concept handbook per module, L6 style), `instructor/moduleNN-<slug>/` (instructors only: the module's demo notebook `dayNN_mN_demo.ipynb` or `.md` plus the project folder or scripts it opens), `learner/moduleNN-<slug>/` (the module's challenge notebook `dayNN_mN_challenge.ipynb` or `.md` plus its project folder or starter files), `instructor/moduleNN-<slug>/challenge-solution/` (instructors only: the challenge done in full with outputs, same file names; user, 2026-10-16) and `dayNN_anchors.md` at the session root; figures in `courseware/common/figures/dayNN/`. Session files carry the `dayNN_` prefix; files beside the anchors keep their module prefix (`m1_…`, `together_…`), and a module may add a named folder. Containers live once in `courseware/common/services/<name>/` (README.md, service.sh, compose.yaml, its INSTRUCTOR.md in `courseware/unit00-programme/instructor/services/<name>/`, `scripts/test-<name>.sh`, and a check in `scripts/test-dev-container.sh`; ports in the registry before it's built), shared by every session; S01's SSH remote is `courseware/common/services/remote-machine/`. **Naming:** the learner activity, its folder, its anchor and its data are all "challenge"; "practice" is retired from every name, path and timing. Demos read the demo data (`courseware/common/data/demo/`, `../../../../common/data/demo` from `instructor/moduleNN-<slug>/`), challenges the challenge data (`courseware/common/data/challenge/`, `../../../../common/data/challenge` from `learner/moduleNN-<slug>/`), and scripts resolve paths from `Path(__file__)`. **Development flow:** handbook → lesson plan → overview → demo → challenges, each written from the one before; the handbook is the source of truth for the topic. **Build order** (user, 2026-10-26): every handbook first, through the source process and approved by the user, then the lesson plan, overview, demo and challenges for all the modules together, never module by module. **Notes:** instructor material lives only under `instructor/` (the lesson plan, the demo and the completed challenge); the inline `::: notes` ruling of 2026-10-14 is superseded. **Connected teaching:** each module builds on the previous one's artefact (S01: Jordan's weekly fund report, written in M1, run remotely in M2, packaged in M3, shipped in Put it together, the optional stretch), and learner text uses triggers, never "in Module N". **Handbook mentions:** each module section of the demo and challenge anchors ends with exactly one "Go deeper" box naming "the Module N handbook" (`nbkit.go_deeper`; exact HTML in [references/conventions.md](references/conventions.md)), with no path, link, section title or number; nothing else in the anchors, the files beside them or their images mentions the handbook. The lesson plan and overview may name "the Module N handbook" but never cite a section. **Handbook numbering:** plain headings and captions; the PDF numbers sections and figures, and prose never says "Figure 1.2" or "section 1.4". **Catalyst** in a handbook appears only inside `::: catalyst` boxes. **Code formatting:** after every code change, `.venv/bin/python scripts/format_code.py <paths>` (isort, black, blacken-docs; settings in `pyproject.toml`); comments that would split a line go above the code (the formatter moves them). **Writing rules** ([references/conventions.md](references/conventions.md) → Writing rules): handbook and overview prose in connected paragraphs with no in-line references (sources only in each section's "Optional further reading"); no "The proper words" line where a figure already labels the mapping; demos visual-first (a module map, then one visual and three to five bullets per beat, code only where a beat runs something); every module opens with the 🧭 anchor (the day has none; user, 2026-10-27), written once in `dayNN_anchors.md` (developers only, never ships) and generated everywhere by `scripts/nbkit.py anchors`, and each challenge section shows one recap visual after its anchor and bridge; one canonical title per unit, day and module, the programme overview's, word for word everywhere, and demo and challenge titles of about six plain words that say what happens (user, 2026-10-27; conventions → Naming's Titles). **Outputs:** nothing is built until the user has reviewed the content; then `scripts/build-session.sh dayNN --reviewed` writes `release/latest/`, laid out exactly like `courseware/` with the PDFs and Word files built in, synced to one Drive folder, `release/latest/`, for instructors (learners don't get Drive; user, 2026-10-27), and released per session with a dated line in `courseware/unit00-programme/instructor/release-notes.md` (user, 2026-10-19; the tree and the sharing: [references/layout.md](references/layout.md) → Built outputs and sharing). Nothing is zipped.

A session is a day of about four hours (user, 2026-10-16, with the correction the same afternoon). The start and end take 30 minutes on the template (user, 2026-10-27): a mandatory 15-minute intro every day (Meet and greet; Jordan and the day, the overview's persona card; What you will be able to do, the overview's outcomes, once a day, and the self-check pacing; setup is pre-work, with a standard Setup check slide and no row), a 5-minute closing debrief and a 10-minute wrap-up (Key takeaways, then Thank you for participating). Every module, with all its activities, is one hour: demo about 20, challenge 20 to 25 in two rows, debrief 5, break 5 to 10. What's left is optional open challenge time: carry on with any module challenge, or take Put it together, the stretch for fast finishers (the last section of the `challenge/` anchor). The format is the lesson-plan skill's. The capstone keeps its three phases. Learner-facing timings use natural denominations (5, 10, 15, 20, 30), plus 25 for the challenge (user, 2026-10-15). Do not publish a timed outline as confirmed until MJB confirms start and end times, breaks and timezone.

Questions are per module (the brief's key questions are the build scope). Outcomes are per session (about five, each mapped to modules in §6's Modules column) and are listed only in `dayNN_overview.md`, with no module tag on any outcome or question; the lesson-plan block names the outcomes each module serves. Per module the definition of done is the seven stages in `reference/subtask-descriptions.md`: Source content · Demo · Challenges · Self-review · Peer-review · Feedback addressed · Learner-facing materials ready. Allowance: 2 developer days per module (1 generation and assets, 1 personal review), about half a day of peer review per module, about 1 day of feedback per unit.

## Persona and exemplar data

- **Firm:** **Harbourline Asset Management**, an invented UK wealth and asset manager. Never a real firm, never CG itself.
- **Character:** **Jordan Mensah**, who works with code and data at Harbourline and is moving into data and AI engineering. **No job title** (user, 2026-10-13): learners arrive with many titles, and a named role makes the programme read as narrower and more technical than it is. **They/them**, as for every invented character. Jordan is the thread, not the hero: one short beat per module ("Jordan has been asked to…"), never a story that the content depends on. Each session's overview introduces Jordan's situation for that session in a persona card straight after its opening paragraph, so learners can relate (user, 2026-10-16; format in `lesson-build` markdown conventions → Overview), and each handbook has its own persona card straight after its intro paragraph, fields Who, This module, What gets in the way, By the end, The examples, with no version numbers (user, 2026-10-19; `lesson-build` markdown conventions → Handbooks).
- **Data:** two **synthetic Morningstar-style fund datasets** with one schema (user, 2026-10-15), generated by `scripts/make_exemplar_data.py` with fixed seeds into `courseware/common/data/demo/` (Harbourline's HLF fund family: the instructor's demo data) and `courseware/common/data/challenge/` (the HLP family: the learners' challenge data) and reused by every module: funds and share classes, daily NAV and returns, holdings, benchmarks, categories and fees, with deliberate quality faults for the data-engineering unit, and a small set of synthetic documents (factsheets, commentary, policy notes) under each dataset's `documents/` for retrieval in S04. Static CSV/Parquet, portable, nothing identifiable. Morningstar data is no longer planned: **CG's open product data** from its public website (MJB supplies it on request) is a possible later dataset, run locally like the other two (MJB, 2026-10-13; user chose synthetic-first the same day; local-only per rule 3, user, 2026-10-16).
- Demo ≠ challenge: demos run on the demo data and challenges on the challenge data, and the challenge applies the module's skill to its own question rather than replaying the demo.
- Use application, website and API examples as well as financial-data pipelines. Do not assume learners are portfolio managers or that forecasting is their job.

## CG rules (apply to every module)

1. **Catalyst first.** Any "at CG" question is answered from Catalyst. If Catalyst does not resolve it, ask Michael on Slack and record the answer in the session digest.
2. **Sensitive messaging: pros and cons, never limitations** (user, 2026-10-19; replaces the MJB gate). Where content discusses tools, platforms or ways of working, present them as comparisons and alternatives with their pros and cons, and say what each is good for, in table headings ("Good for", "Trade-offs") and FAQs too; never highlight a tool's limitations or weaknesses. Teach review, checks and accountability as good engineering practice that every change gets, not as a fix for a tool's flaws. No `<!-- sensitive: … -->` markers: write it right the first time. A planted-fault file is a first draft to review, never Copilot's mistakes. Content files never name MJB or anyone else (user, 2026-10-15). Constructive tone, CG-specific context.
3. **Local containers, no CG-access notes** (user, 2026-10-16). Every demo and challenge runs on static data in containers running locally on the learner's laptop: the dev container the course folder opens in, and the services in `courseware/common/services/` (S01's remote machine on `localhost`, `host.docker.internal` from inside the dev container). Content never carries a "Needs CG access" section, a `::: blocked` callout, an "until CG answers" caveat, a mirror-container fallback, a "check on a CG laptop" or an Asana reference, and it says "the dev container", never "the CG dev container". Anything that depends on CG (its Copilot settings, registries, laptops, platform access) is tracked outside the content, in Asana, and never written into it; nothing waits for it. CG context that is content stays: Catalyst boxes, Harness as CG's CI/CD platform, CG's VS Code and Copilot workflow. `module-audit` warns on any CG-access note, and the build refuses a `::: blocked` callout, a `<!-- blocked: -->` marker or "Needs CG access" in anything it ships, lesson plan included. This is the rule's one statement; other skills point here.
4. **Reuse before redevelop.** Fundamentals modules, AI Accelerator sessions, existing platform/dbt/orchestration content, the Deloitte GenAI reference (`reference/Deloitte/GenAI`), DataCreators v4 and client material (`reference/DataCreators-*`), Catalyst resources.
5. **Motivate before teaching comprehensively.** Start from the brief's questions and a useful output; exemplar first, use AI to understand it, then explore selected methods.
6. **Essential learning inside the workshop.** Nothing optional (appendices, extra reading) is ever a prerequisite.
7. **Avoid unnecessary perfection.** Coherent, deliverable content that iterates from pilot evidence.
8. **AI-assisted engineering is a thread, not a module.** Copilot is set up in S01 M1 and every later module carries one AI-assisted beat in its demo and one in its challenge: plan → generate → review → validate. Every prompt learners or instructors are given sits in the standard 🤖 COPILOT box, with its mode, model and attach badges (user, 2026-10-16; `references/conventions.md` → "The Copilot box"). The learner appendix *Working with Copilot* and the one-page quick reference (`courseware/common/appendices/`) are the reference; CG's enabled models and settings come from Catalyst or Michael, and how tools are compared follows CG rule 2.
9. **Nothing identifiable, no absolute paths, no real keys** in anything shipped.
10. **Keep it simple** (user, 2026-10-26; S02's rule zero). For instructors and learners, choose the fewest files, folders, services, accounts, commands and steps that still deliver the outcome. At every design fork, ask "is this the simplest version that works?", and cut scope before adding machinery. Every builder and reviewer brief asks it (S02: one `requirements.txt`, not two; one branch rule, extended in Module 6; the challenge pipeline runs the tests only).
11. **Be specific, define first** (user, 2026-10-27; Decoded-wide in `courseware-conventions`). A reference back names the file, the command and what it shows; every term is defined at first use in each file before any shorthand (test-driven development (TDD) before "test-first"); testing levels are named where tests appear.
