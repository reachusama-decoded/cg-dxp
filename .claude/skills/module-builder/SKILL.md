# Module builder (orchestrator)

Builds a CG Core session, or one module of it, in the approval-gated order the programme tracks in Asana, following the development flow the user set on 2026-10-15 and the build order set on 2026-10-26. Each stage is its own skill; this skill sequences them and keeps the definition of done in front of you: [references/session-checklist.md](references/session-checklist.md), the rules learned building Session 02, checked from start to handover.

## The development flow

**handbook → lesson plan → overview → demo → challenges**

Each step is written from the one before it. The handbook is the source of truth for concepts, names, numbers and order; the lesson-plan block teaches from it; the overview is written from the lesson plan; the demo shows what the handbook explains in the order the lesson plan gives; the challenge applies the demo's skill to the challenge data. A change found later (a number that differs on a run, a renamed step) is fixed at the earliest step it touches and mirrored downstream in the same pass.

**Build order** (user, 2026-10-26, from S02). The flow says what each file is written *from*; it is not a build sequence. A session is built in two phases, never module by module:

1. **Phase 1, the handbooks.** Every module's handbook goes through `module-source`'s source process (research sweep, wide draft, visuals, independent pedagogical review, reduce and refine), the modules in parallel, until the user has approved every handbook of the session.
2. **Phase 2, everything downstream together.** The lesson plan, overview, demo, challenge and completed challenge for every module, from the approved handbooks. Then the tooling, the independent read-through and the user's review of the whole session.

The Asana board keeps its stages as they are (`reference/subtask-descriptions.md`, unchanged): the "Source content" stage's lesson-plan rows and overview entries are completed in phase 2, so tick that subtask when they exist, not when the handbook is approved.

The teaching connects: each module builds on the previous one's artefact (S01: Jordan's weekly fund report, written in M1, run on a remote machine over SSH in M2, packaged with a pinned environment in M3, shipped in Put it together, the optional stretch). The lesson plan gives every block a bridge in and a bridge out, and each module section of the demo and challenge opens with its 🧭 anchor (generated from `dayNN_anchors.md`), then a bridge cell ("This builds on …", naming the project, the numbers and the repository, plus one line into the map), then the module map, each in its own cell (`programme-profile/references/conventions.md` → "Every module opens with the 🧭 anchor"), so every session feels the same and reads as one piece of work. Where a module's skill matters beyond the laptop, the handbook connects it to real deployment (S02 M6: the same image runs on the laptop, in the pipeline, in staging and in production, with only its settings, size and front door changing).

The writing rules travel with the flow (`programme-profile/references/conventions.md` → Writing rules, and Handbook numbering, handbook mentions, naming and formatting): the handbook is connected prose with sources only in its further reading, plain headings and captions that the PDF numbers, and Catalyst only inside its boxes; the lesson plan is short spoken lines; the overview's prose is connected and unreferenced, with no module tags on outcomes or questions, and a self-check of at most three questions, one per module, that the lesson plan's welcome uses to pace each module; the lesson plan and overview may name "the Module N handbook" but never cite a section; the demo is visual-first (module map, one visual and three to five bullets per beat); each challenge section shows one recap visual (the module map) after its anchor and bridge, before its first task; each module section of the demo and challenge ends with one Go deeper box (`nbkit.go_deeper`), the only place they mention the handbook. No "The proper words" line repeats a mapping a figure already labels; a figure whose rows explain something (Dockerfile lines and the layers they make) lines its rows up with the thing it explains. A config file the demo opens (a Dockerfile, a pipeline file) gets a plain line-by-line table in the file's own order: each line and what it does, one short sentence each. The activity and its data are "challenge", never "practice". Code is formatted with `scripts/format_code.py` after every change, which moves any comment that would split a line above its code. Every reference back names the file, the command and what it shows; every term is defined before any shorthand for it; tools are compared by pros and cons, in table headings and FAQs too; and every design is the simplest version that works (session checklist items 10 to 14).

## 0. Before anything

1. Read `programme-profile` (SKILL.md, `references/layout.md`, `references/structure.md`, `references/conventions.md`) and the digest for this session and its neighbours.
2. Read `internal-programme-overview.md` §6 for this session's questions and outcomes and which modules deliver them, then `reference/subtask-descriptions.md`. The **Module task** section is the build brief; each later section is the done-when for a stage (read with the build order above).
3. Read each module's brief in `designer/core/transcripts/cg-design-core.md` at the line structure.md gives: key questions, proposed challenge, TODOs. A TODO(MJB) that a module depends on is raised in Asana and the module is built on local containers meanwhile, not silently resolved and never noted in the content.
4. Read the session folder as it stands, and the previous session's last artefact: that is what this session builds on.
5. Confirm both datasets exist (`courseware/common/data/demo/`, `courseware/common/data/challenge/`). If not, the first job is `scripts/make_exemplar_data.py`.
6. Read [references/session-checklist.md](references/session-checklist.md).
7. Scout the repo, the brief and the neighbouring sessions, then ask the user once, in one batch (AskUserQuestion), each fork with the recommended option first and marked "(Recommended)"; then build without further check-ins.
8. Plan the work to run in parallel by file ownership (one agent per handbook in phase 1, one per notebook or file in phase 2), writers and reviewers at full effort, no review or check dropped. Launch a workflow in the same turn as the request it serves: subagents act only on the user's latest message.

## 1. Stages

Two user gates: every handbook of the session (before phase 2), and the whole session after the independent read-through (before any build, sync or commit). Ask at genuine design forks (scope cut, which key question becomes the challenge, what to raise with CG) in one batch, recommended option first (§0). In phase 2, stages 2 and 3, and stage 1's lesson-plan and overview steps, run for every module together.

## 2. Session assembly

Phase 1 adds the handbooks, their figures and research packs. Phase 2 adds every module's lesson-plan rows, overview entries, demo and challenge sections, the completed challenge and the put-it-together task together, so the folder is complete when phase 2 ends. No placeholder sections. At the start of phase 2:

1. Create `dayNN_anchors.md` (one `## mN` per module and `## together`, no `## day`: the day-level anchor is retired, user 2026-10-27; each with title, question, what, why and how, written from the approved handbooks), then `learner/module00-overview/dayNN_overview.md`, `instructor/module00-overview/dayNN_lesson_plan.md` (copied from the `lesson-plan` skill's `assets/lesson-plan-template.md`), and the two notebook anchors with their title, how-to-use and footer cells (`lesson-build`). `scripts/nbkit.py anchors --session <folder>` writes every copy of the 🧭 anchors; the copies are never typed or edited.
2. Write the put-it-together task as its own challenge notebook in its own module folder (`learner/module99-put-it-together/dayNN_together_challenge.ipynb`, numbered 99 so it bookends `module00-overview/`), starting from a state that a learner who stopped at Q1 or Q2 of each module can reach, with its Put it together reference and the open challenge time rows in the lesson plan (the optional stretch there).
3. When phase 2 is done and the tooling is clean, commission the independent read-through (checklist item 24; `module-review` → Session read-through): a reviewer who didn't build the session reads it as a learner and as an instructor and writes `reference/cg-core-research/dayNN/session-read-through-<date>.md`. Apply every must-fix, take each should-improve that is a design choice to the user, and rerun the tooling.
4. Run the checklist's part E. Record every user ruling of the build in `programme-profile/digest/dayNN.md`, dated and marked (user), and each programme-wide one in `programme-profile/references/conventions.md`. Then present the session for the user's review: nothing is built, synced or committed before the user asks.

## 3. After every stage

- Run the tooling the stage touched (checklist item 23): `scripts/audit.py` to 0 errors and 0 warnings, `scripts/format_code.py --check`, `scripts/nbkit.py toc --nb <notebook> --check` for each notebook, `scripts/nbkit.py anchors --session <folder> --check`, and `scripts/test-dev-container.sh` with each `scripts/test-<service>.sh` whenever pins or services changed (`scripts/check-session.sh dayNN` runs them all in one go).
- Run `.venv/bin/python scripts/format_code.py <changed paths>` after any code change and finish with `--check` passing.
- Update the Asana subtask (the user does this; give them the one-line status and anything to raise with CG).
- Record decisions that constrain other modules in the session digest; programme-wide rulings in `programme-profile/references/conventions.md`; Decoded-wide ones in `courseware-conventions`.
- Add any new port to `programme-profile/references/stack.md` before its service is built, any new dataset to `structure.md`, and any new pin to `courseware/.devcontainer/requirements.txt` (each project's `requirements.txt` matches it). Build a new service in the shape `programme-profile/references/layout.md` → Services gives, with its `scripts/test-<service>.sh` and a check in `scripts/test-dev-container.sh`.

## 4. Dependencies on CG

Nothing waits for CG. Every demo and challenge runs on the dev container and the local services (`programme-profile` rule 3; user, 2026-10-16), so a question for CG, a vendor decision or an answer from CG's programme contact never stalls the module and never appears in it: no "Needs CG access" section, `::: blocked` callout, "until CG answers" caveat or Asana reference in any file. Tell the user what to raise in Asana (owner, what is needed, which modules it touches) and continue.
