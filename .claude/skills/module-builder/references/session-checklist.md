# Session checklist

What every CG Core session is built and checked against. The rules come from building Session 02 (user rulings of 2026-10-26 and 2026-10-27, in `programme-profile/digest/day02.md`). They apply to every session; S02 appears only in short examples. Each item names where it is enforced: a skill, a script, or a reviewer's judgement.

Parts A and B shape the work before it starts, parts C and D apply while it's built, and part E is the gate before the user's review.

**Before item 1.** Scout the repo, the brief and the neighbouring sessions, then ask the user once, in one batch, each fork with the recommended option first; then build without further check-ins. Go faster by running independent work in parallel (one agent per handbook, then per file), never by lowering effort or dropping a review or a check. Launch any workflow in the same turn as the request it serves.

## A. Source content, before any downstream file

1. **Research sweep first.** Before drafting a handbook, a research agent with web search sweeps vendor docs, articles, standards and good-practice guides, and internal material (Catalyst, AIA, Fundamentals, the GenAI reference). It writes `reference/cg-core-research/dayNN/mN-<slug>/deep-research-<date>.md`: a gap table, proposed additions each sized for simplicity, the Catalyst rules that apply, further reading and any errors in the current text. *module-source Stage A.*
2. **Every link recorded.** The same folder's `references.md` lists every link with its URL, the date it was checked, what it is and what was taken from it. Every link in the handbook (further reading and appendix included) appears there. *module-source; the audit.*
3. **Wide draft, then visuals.** `draft.md` in the research folder is organised by the brief's key questions and the outcomes the module serves, with more than will ship. Diagrams and screenshots are added where they help learning. A figure whose rows explain something lines its rows up with the thing it explains (each group of Dockerfile lines level with the part of the image it makes). *module-source.*
4. **Independent pedagogical review.** A reviewer who didn't write the draft, never the author, writes `pedagogical-review.md` in the research folder. It covers missing foundations, overload, sequencing, suitability for adult learners, simplicity, vagueness and define-first, each finding as a must-fix, a should-improve or a cut. A self-check never stands in for it. *module-review → Pedagogical review.*
5. **Reduce and refine.** The handbook is the source of truth for its topic: 3,000 to 12,000 learner words, aiming for about 7,000, and past 7,000 only for topic knowledge. Only delivery detail (click paths, room logistics, what to run when) moves to the lesson plan. Truly optional depth goes to an appendix at the end of the same file, after the Summary, which opens by saying that nothing in it is needed for the module, its exercises or its outcomes. `notes.md` records what moved where. (S02: Module 6's operator-level detail went to "Going further with containers".) *module-source; `audit.py` checks the range.*
6. **User approval gates.** The user approves every handbook of the session before anything downstream is built. Then the lesson plan, overview, demo, challenge and completed challenge are built together for all the modules, never module by module. A later change lands in the handbook first and flows down in the same pass. (The Asana "Source content" stage keeps its wording; its lesson-plan and overview items are completed in this later pass.) *module-builder.*

## B. Openings: the 🧭 anchor

7. **The anchor.** Every module opens with the 🧭 anchor, headed "🧭 WHAT, WHY AND HOW" (the day has none; user, 2026-10-27): a question from the learner's own work, then **What** (the tool or idea, named and defined in plain words), **Why** (what it does for a team first, then for Jordan's report) and **How** (what happens in the module), each one clear sentence of at most 30 words, the same words on the slides' tiles (user, 2026-10-27), never a content dump. The challenge's anchor is identical to the demo's: a recap, on top of the challenge's own sections. The words live once, in `dayNN_anchors.md` (`## mN`, `## together`; no `## day`), which never ships. `scripts/nbkit.py anchors --session <folder>` writes every copy, and the copies are never edited. In a notebook a module section runs heading cell · anchor cell · bridge cell ("This builds on …", naming the project, numbers and repository, plus one line into the map) · module map cell, each its own cell, so the heading, the box and the map never crowd each other. The lesson plan's first Say for the module asks the anchor's question. (S02 Module 5: "Have you ever emailed `report_final_v2.py` to a colleague, or needed last Tuesday's version back?") *conventions.md; `nbkit.py anchors --check` and the audit.*
8. **Handbooks.** Each handbook carries its module's anchor straight after the persona card. The card stays as it is, with its module rows: broad, and separate from the anchor. *module-source; the anchor's checks.*
9. **Overview and lesson plan.** The overview carries no anchor, the day's or a module's (user, 2026-10-27; nbkit removes any old one). Each lesson-plan module section opens with the module's anchor, which the Word build draws; no **Module outcomes.** (outcomes appear once, in the intro; user, 2026-10-27). *module-source Stage D, lesson-plan.*

## C. Writing

10. **Be specific.** A reference back names the file, the command and what it shows (S02: "`python fund_report.py > report.txt` once, then `python fund_report.py | diff report.txt -`, silent while they match"). Never "a check", "a saved copy" or "the earlier work". A config file the demo opens (a Dockerfile, a pipeline file) gets a plain line-by-line table in the file's own order. Check openings, taglines, persona cards, covers lists and Say lines first. *Reviewers; `courseware-conventions` (Decoded-wide).*
11. **Define first.** Every term and method is named and defined in plain words at its first use in each file, before any shorthand for it (test-driven development (TDD) before "test-first"; fixture, pin, squash merge, pull request). Each anchor, handbook and lesson plan stands alone, so each defines its own terms. *Reviewers; the audit's shorthand list; `courseware-conventions` (Decoded-wide).*
12. **Name the testing levels where they occur.** Wherever a session writes or runs tests, say which are unit, integration and end-to-end smoke tests, and what each level is good for. *Reviewers.*
13. **Keep it simple (rule zero).** The fewest files, folders, services, accounts, commands and steps that still deliver the outcome, for instructors and learners alike. At every fork, ask "is this the simplest version that works?", and cut scope before adding machinery. (S02: one `requirements.txt`, not two; one branch rule, extended in Module 6.) *Every builder and reviewer brief.*
14. **Pros and cons only.** Tools, platforms and ways of working are compared by their pros and cons and what each is good for, never by their limitations. That includes table headings ("Good for" and "Trade-offs") and the lesson plan's FAQs. *CG rule 2; the audit.*

14a. **Titles** (user, 2026-10-27). Each unit, day and module has one canonical title, the programme overview's ("Programme at a glance"), word for word in every heading, breadcrumb, lesson-plan section, overview, handbook H1, the anchors' Title, slide and agenda; never shortened or re-cased. Demo headings, challenge section titles and task titles are about six words or fewer, say what happens, in plain words, with no metaphor or teaser and no question mark ("Test and fix the returns code", not "Test it, then fix it"). *The audit (`check_canonical_titles`; a warning on a demo heading over seven words or ending in "?").*

**Also: connect to real use.** Where a module's skill matters beyond the laptop, the handbook says how it carries on into the team's real environments, at concept level (S02 Module 6: the same image runs on the laptop, in the pipeline, in staging and in production; only settings, secrets, data, size and the front door change). *Reviewers.*

## D. Build and evidence

15. **One starting folder per module.** A module that works on a project starts from its own folder beside its notebook, in `instructor/moduleNN-<slug>/` and in `learner/moduleNN-<slug>/` (`mN_<project>/`), complete as the module begins, so anyone who falls behind can start the module fresh. A folder or repository that a later task continues in is named once and called the same in every file. (S02: the challenge's repository is always `m5_fund_report/`, `fund-report-challenge` on Harness.) *module-demo, module-challenge.*
16. **Challenge faults differ from the demo.** The challenge plants its own faults, never the demo's in another form, and runs on the challenge data. *module-challenge; reviewers.*
17. **Evidence for every outcome.** Each clause of each outcome a module serves has evidence in a challenge task, with the core clauses at Q1 or Q2. A clause evidenced only in the demo or the debrief is said so in the lesson plan's Objectives table. (S02: outcome 2's refactoring.) *module-challenge, lesson-plan; the audit.*
18. **Put it together starts from a reachable state.** It starts from a state that a learner who stopped at Q1 or Q2 of each module can reach, and its first lines name that state (the files, the repository, the branch). *module-challenge; reviewers.*
19. **Timing, and the lesson plan mirrors the notebooks.** One lesson-plan row per demo `### ` heading across the day's module demo notebooks, its title that heading word for word, in the same order, nothing skipped or grouped; a module's closing lines end its last beat and are not a heading; the lesson plan's module section titles are the demo's `## Module` headings, and each module's first challenge row is titled with the challenge's section title and names its Q1–Q3 task titles exactly (user, 2026-10-27; the audit fails on drift). Rows run in 2.5-minute steps (start `0:12:30` on a half minute) so every heading fits and the demo still totals about 20 minutes. Each demo row fits its minutes on a real run. Slow steps (pushes, pipeline runs, first image builds or pulls) are pre-run in the break before the module: the break row and the checklist say what to run, and the demo row's note says it ran in the break. The images a session needs are pulled at setup. Paired challenges run in parallel, each partner on their own laptop and copy, and swap only for the review. Q1 fits the challenge time for most of the room. Each module has two 2.5-minute Questioning rows (user, 2026-10-27): one straight after the demo's last beat, its minutes taken by shortening one 5-minute demo beat, and one between the challenge's two rows, taken from the second; each has Ask (one or two questions that make learners think), Listen for and If stuck. The day is five hours, 0:00 to 5:00 (user, 2026-11-02). It opens with the mandatory 25-minute intro (user, 2026-11-02): Arrive and settle (Intro/Outro, 5), Welcome (Intro/Outro, 15; a unit's first day, Day 01, 03, 05, 07, runs the welcome day's plan inside it from its own deck, beside the day's, and the day's deck has one Welcome slide, `dayNN-welcome`; user, 2026-11-02: kept separate) or Welcome back (Intro/Outro, 15; its second day, Day 02, 04, 06, 08), Jordan and the day (Explain, 2.5, **From the overview.** the persona card) and What you will be able to do (Explain, 2.5, **From the overview.** the outcomes); no Setup check or Meet and greet row. Each module is 75 minutes, with a Shareback/questions row (Feedback and discussion, exactly 15; user, 2026-11-02, replacing the 10-minute Catch-up and questions row, which now fails) after its last challenge row and straight before its debrief; modules run 0:25 to 1:40, 1:40 to 2:55 and 2:55 to 4:10 (user, 2026-11-02), open challenge time 4:10 to 4:40 (Independent or pairs work rows only). It ends with the Wrap-up: Closing debrief and questions (Feedback and discussion, 10: blockers, anything shipped, the questions the day has left), Key takeaways (Feedback and discussion, 5, a brief look back at the outcomes, then one takeaway per module) and Thank you for participating (Intro/Outro, 5: the thanks, the feedback form, the next session). The audit fails on a missing Questioning, shareback, intro or ending row, or a quote that differs from the overview, and warns on a module or open challenge time off its start time. *module-demo, module-challenge, lesson-plan.*
19a. **Slides after the lesson plan.** Once the plan is final, `scripts/make_slides.py draft dayNN` writes `instructor/module00-overview/dayNN_slides.md`; tune it by hand, then `make_slides.py check dayNN` passes and `make_slides.py build dayNN` builds with no fit failure. A later change to the lesson plan is followed in the same pass by `make_slides.py sync dayNN` (new slides added, titles, notes and timed slots refreshed, frame slides rewritten whole, hand-tuned bodies and **Detail:** notes kept), then `check dayNN`. Running order (user, 2026-11-02): cover · Arrive and settle (the standard slide, the same in every unit and day, id `arrive-and-settle`, for the plan's Arrive and settle row: `full-visual`, the usual title at the top over the shared picture `common/figures/shared/setup-check.png` on yellow (alt text as an attribute, `![](…){alt="…"}`, so no caption is drawn) and no other text, its notes the setup cue; drawn by `scripts/figures/shared_setup_check.py` with `brand.slide_figure()`) · the welcome: on a unit's first day (a `Welcome` row) one drafted `dayNN-welcome` title-body slide, Welcome, while the welcome itself runs from its own deck, `day00_slides.pptx`, beside the day's (user, 2026-11-02: kept separate); on its second day (a `Welcome back` row) one drafted `dayNN-welcome-back` title-body slide · Jordan and the day (Decoded's `table` layout: a short phrase a row, the card word for word in the notes) · What you will be able to do (a table: a short phrase per outcome, each outcome word for word in the notes; outcomes appear once a day) · Today (`agenda-3` tiles on the yellow photograph: "Module 01", the full canonical title, never shortened, then the module in one short line, the anchors file's **In short:**; a title that needs three lines is built with a stand-in and placed by `make_slides.py` with its caption moved down, user 2026-10-27) · per module: divider (`section-divider-photo`, the same yellow photograph as Today: "#1" and the canonical title) · the module's question (`statement`) · What, why and how (`recap-3` tiles, the anchors file's short phrases; the anchor word for word in the notes) · map · one slide per demo heading · a think slide (the first Ask's question as the title, its lead-in and any second Ask as prompts) · challenge brief and continuation · Shareback/questions (`challenge-continuation`, id `dayNN-mN-shareback`, drafted from the row's On screen points or Purpose, hand-tunable; user, 2026-11-02; sync retires the old `dayNN-mN-catch-up`) · debrief · break · Put it together · Closing debrief and questions (the Wrap-up's first row, id `dayNN-closing-debrief`) · Key takeaways · Thank you for participating (title and photo only; the feedback form stays in the notes, never on the slide). No Meet and greet or Setup check slide, no day-level question or what, why and how slide, no module objectives slide (user, 2026-10-27; 2026-11-02). **Concise slides** (user, 2026-10-27, like Fundamentals'): a title of 8 words or fewer (canonical titles and a statement slide's question exempt), at most 3 bullets a slot, each bullet, line or table cell 12 words or fewer; the rest goes in the speaker notes (**Detail:**, **Say:**), so nothing is lost. The generator drafts to it (`short`, `concise`) and `make_slides.py check` and the audit fail on longer text (`concise_problems`). The release ships `dayNN_slides.pptx` and `dayNN_slides.pdf` (user, 2026-10-27). *lesson-plan; lesson-build; the audit.*
20. **Real outputs only.** Every quoted output (handbook, demo, lesson plan, completed challenge) comes from a real run in the dev container image: the dev container, or a throwaway container from its image. `.venv/bin/python` stays fine for quick checks and tooling, never for an output that's quoted. Re-run every affected output after any pin, data or code change, and never hand-edit an output. *module-source, module-demo, module-challenge.*
21. **Pins.** `courseware/.devcontainer/requirements.txt` is the one list of versions. Each project folder keeps its own `requirements.txt`, and its pins, pipelines' install steps, Dockerfiles' base images and versions quoted in handbooks all match the dev container's. New pins are resolved with every transitive dependency pinned and nothing newer than about two weeks old, and `pip check` is clean. No warning appears in learner-visible output: change the pin or the code rather than hide it. *stack.md → Pins; `scripts/check_pins.py`.* Any change to `courseware/.devcontainer/` (a new session's pins included) can change outputs other sessions quote (package counts, `pip freeze`, versions): re-run every session's environment outputs in the dev container and update them, then run `check-session.sh` for every built session (S02's pins changed S01's freeze count from 39 to 60, 2026-10-27). Every image is pinned to an exact version tag (Harness's clone image by digest, in its `service.sh`); a security fix overrides the two-week rule (user, 2026-10-27).
22. **Services.** Each service lives in `courseware/common/services/<name>/` with `service.sh` and a learner `README.md`, its instructor notes in `courseware/unit00-programme/instructor/services/<name>/INSTRUCTOR.md`, and has a test in `scripts/` (`test-<name>.sh`) that builds it, runs what the sessions teach and tears it down. `scripts/test-dev-container.sh` starts it from inside the dev container. Its ports go in the port registry before it's built, and the overview's Services line names it. *layout.md → Services; the audit.*
22a. **Layout.** The session follows `programme-profile/references/layout.md` (2026-10-27): `learner/` and `instructor/` are each split into module folders (user, 2026-10-27): `module00-overview/` (the overview; the lesson plan), then `moduleNN-<slug>/` per module, numbered unit-wide (learner: the handbook, `dayNN_mN_challenge.ipynb` and its project folder, directly in the module folder; instructor: `dayNN_mN_demo.ipynb` with its project folders and `challenge-solution/`), and Put it together in `module99-put-it-together/` (numbered 99 so it bookends `module00-overview/`); every module notebook is self-contained, opening with nbkit's short, identical header; `dayNN_anchors.md` sits at the session root; figures in `courseware/common/figures/dayNN/`, data and services in `courseware/common/`; no learner file links into `instructor/`.

## E. Checks before handing over

23. **Tooling clean.** `scripts/check-session.sh dayNN` passes: `scripts/audit.py` shows 0 errors and 0 warnings (a false positive is fixed in the script, never left), `scripts/format_code.py --check` passes, `scripts/nbkit.py toc --check` and `nbkit.py anchors --check` pass for every notebook and the session, `scripts/check_pins.py` is clean, and `scripts/test-dev-container.sh` and every service test the session uses pass. *module-audit.*
24. **Independent read-through.** A reviewer who didn't build the session reads it end to end, once as a learner (overview, handbooks, demo, challenge) and once as an instructor (the lesson plan, followed into the anchors). It checks the thread and transitions, timing (rows, pre-runs, pairs), simplicity, consistency of names, numbers and folders, outcome evidence (items 17 and 18), the content rules, vagueness and define-first. It writes `reference/cg-core-research/dayNN/session-read-through-<date>.md` (must-fix and should-improve, with locations). Every must-fix is applied and the tooling rerun before the user's review. *module-review → Session read-through.*
25. **Records.** The session digest records every user ruling, dated and marked (user). Programme-wide rules go in `programme-profile/references/conventions.md` (or the skill that owns them). Review reports (deep research, pedagogical, peer, read-through) live in `reference/cg-core-research/`. Nothing is built, synced or committed until the user has reviewed the content and asked. *programme-profile → Recording decisions.*

**Review log.** Every review comment from the user gets a row in `reference/reviews/user-review-log.md` (date, comment, what changed, skills updated, status), and the skills change in the same pass (user, 2026-10-27).

**Security.** Security fixes override the two-week pin rule (the dev container's pip date moves forward to admit them); every image is pinned to an exact tag, including images a service pulls itself; image scans and a Python dependency audit run before each release (user, 2026-10-27).
