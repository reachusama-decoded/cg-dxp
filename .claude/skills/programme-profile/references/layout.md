# CG Core repo layout (user-confirmed 2026-10-14; session folder and development flow 2026-10-15; folder structure 2026-10-27)

Markdown, notebooks and scripts are the source. `courseware/` holds the course as it is written; the build turns it into one tree, `release/latest/`, laid out exactly like `courseware/` with every PDF and Word file built in (user, 2026-10-27, aligned with the Fundamentals programme's `courseware/` and `release/`, `reference/ts-cg-fundamentals/`). Inside both trees, learner and instructor material are split by folder: every session has a `learner/` folder (overview, handbooks, challenge) and an `instructor/` folder (lesson plan, demo, completed challenge), and everything shared (data, services, figures) lives once in `common/`. Every session has the same shape, so a developer, a reviewer and an instructor can find one module's material without reading anything else, and every session feels the same to a learner. The session shape is modelled on the AI Accelerator's Unit 3 Session 12 (`reference/aia-content-backup/Unit 3: Building ML and AI Products/Session 12/`).

## The development flow

Every module is developed in this order, each step written from the one before it (user, 2026-10-15):

**handbook → lesson plan → overview → demo → challenges**

The handbook is the source of truth for concepts, names, numbers and order. The lesson plan block is written from the handbook; the overview's agenda, outcomes and questions from the lesson plan; the demo section from the handbook and the lesson plan; the challenge section from the demo. A change upstream is mirrored downstream in the same pass.

The build order is every handbook first, through the source process and approved by the user, then the lesson plan, overview, demo and challenges for all the modules together (user, 2026-10-26).

## Connected teaching

Each module builds on the previous one's artefact, and every session runs the same way. In S01 the thread is Jordan's weekly fund report: written in M1 (notebook, then a script with a recorded check), run on a remote Linux machine over SSH with logs in M2, packaged with a pinned environment in M3, shipped in Put it together, the optional stretch. The lesson plan gives every block a bridge in and a bridge out; each module section of the demo and the challenge opens with its 🧭 anchor and a bridge ("This builds on …", naming the project, numbers and repository). Learner-facing text never names a later module or session as where something is taught: it uses a trigger ("as soon as the script has to run somewhere else"). Instructor text may name modules.

## Services

Every container the course runs (S01's SSH remote, S02's Harness server; Airflow and others later) lives once in `courseware/common/services/<name>/` and is shared by every session's demos and challenges, so learners who run a demo and a challenge use the same machine and there is one copy to maintain (user, 2026-10-15). Each service folder has the same shape:

- **A hyphenated name** saying what it is (`remote-machine`, `airflow`).
- **`README.md`**, learner-facing: what it is and which sessions use it, the quick way, step by step, what's on it and a troubleshooting table. Never a CG-access note: the service runs locally and content needs nothing from CG (profile rule 3, user, 2026-10-16).
- **Its instructor notes**, `courseware/unit00-programme/instructor/services/<name>/INSTRUCTOR.md` (user, 2026-10-16; moved 2026-10-27): when to start it and what to show from it. `common/` holds no instructor material.
- **`service.sh`**: `bash service.sh start | status | logs | stop | reset`, plus any extras the service needs (`connect` for the remote machine). It works from any folder. Learners run it in VS Code's terminal inside the dev container (`courseware/.devcontainer/`, user, 2026-10-16), whose `remoteEnv` gives Docker the laptop's paths and whose docker CLI talks to the laptop's Docker; it reaches services at `host.docker.internal` there, and refuses to start a service in any other container that doesn't give it the laptop's paths. The laptop's own terminal (`localhost`) is the README's one fallback line. A new service's paths go into the dev container's `remoteEnv`, and `scripts/test-dev-container.sh` checks it starts from inside.
- **`compose.yaml`**, plus a `Dockerfile` only when an image has to be built, and the files the image needs. Ports come from the port registry and are published on `127.0.0.1` only; the datasets are mounted read-only from `../../data` (`courseware/common/data/`); keys and secrets live in a git-ignored folder and are never committed.
- **`scripts/test-<service>.sh`**: an end-to-end check that builds it, runs what the sessions teach and tears it down. Rerun it after any change to the service.
- **A check in `scripts/test-dev-container.sh`** that starts it from inside the dev container and reaches it (S02: Harness at `host.docker.internal:3000`), and **its ports in the registry** (`stack.md`) before it's built. The audit checks the full shape for every service the overview names (sessions on the template).

Each session's overview names the services it uses in one line under "Set up at the start of the day" ("**Services this session uses:** `common/services/remote-machine/` …", or "none"), and the steps under it start each one (S01: "Step 4 below starts it"), because start-here tells learners the overview's setup steps start a session's services (user, 2026-10-19), and each service's README lists the sessions that use it. Session-specific pieces (S08's pipelines, a session's eval cases) live in that session's `instructor/moduleNN-<slug>/` or `learner/moduleNN-<slug>/` folder and the service loads them when it starts, so a service never forks per session; a service that must differ substantially becomes a second service with its own name. Session files point at a service by its place in the course (`common/services/remote-machine/`); from a session's `instructor/moduleNN-<slug>/` or `learner/moduleNN-<slug>/` folder that is `../../../../common/services/remote-machine/` (one more `../` from a project folder inside it). Starting a service is part of a session's setup, not a demo step, so a challenge may use it without anything from the demo having run.

## Naming

- Session folders: `dayNN-<slug>`; handbooks `learner/moduleNN-<slug>/m<N>-<slug>.md` with the brief's unit-relative module number; capstone phases `p<N>-<slug>`.
- Session files carry the session prefix (user, 2026-10-15), so an editor tab shows which session a file belongs to: `learner/module00-overview/dayNN_overview.md`, `instructor/module00-overview/dayNN_lesson_plan.md`, `instructor/moduleNN-<slug>/dayNN_mN_demo.ipynb` (or `.md`), `learner/moduleNN-<slug>/dayNN_mN_challenge.ipynb` (or `.md`), and `dayNN_anchors.md` at the session folder's root.
- One word, "challenge", names the learner activity, its folder, its anchor and its data; "practice" is retired from every name, path and timing ("25 challenge"). Plain English such as "in practice" stays.
- One word, "instructor", names the person who delivers and their material (user, 2026-10-27; it replaces the earlier word everywhere): `instructor/` folders, "Instructor-led demo", "Instructor notes", `INSTRUCTOR.md`.
- Slugs: lowercase, hyphens, from the brief's module title, at most five words.
- Files a module adds to `instructor/moduleNN-<slug>/` or `learner/moduleNN-<slug>/` keep the module prefix, not the session prefix: one file carries it with underscores (`m1_fund_report_reviewed.py`, `m3_requirements.txt`); several files go in a named folder. Containers never go in a session folder: they live once in `courseware/common/services/` (see Services). Put-it-together starter files use `together_` or a `together/` folder. The anchors are always `dayNN_mN_demo.ipynb` / `dayNN_mN_demo.md` and `dayNN_mN_challenge.ipynb` / `dayNN_mN_challenge.md`. A module that works on a project starts from its own folder, `mN_<project>/`, in `instructor/moduleNN-<slug>/` and in `learner/moduleNN-<slug>/` (user, 2026-10-26), complete as the module begins so anyone behind starts it fresh; a folder a later task continues in is named once and called the same everywhere (S02: `m4_fund_report/`, `m5_fund_report/`, `m6_fund_report/`).
- Figures: `courseware/common/figures/dayNN/mN-<what>.png` (or `.svg`), one folder per session (user, 2026-10-27), referenced from a handbook, `instructor/moduleNN-<slug>/` or `learner/moduleNN-<slug>/` as `../../../../common/figures/dayNN/mN-<what>.png` and from the overview as `../../../common/figures/dayNN/mN-<what>.png`; the script that made it is `scripts/figures/dayNN/mN_<what>.py`. Demo concept cards and module maps live there too (`m1-map.png`, `m1-card-<what>.png`).
- The demo's 🏆 CHALLENGE TIME box links the learners' challenge as `../../learner/moduleNN-<slug>/dayNN_mN_challenge.ipynb`: `release/latest/` mirrors `courseware/`, so the link is the same in both trees.
- No placeholder sections or files for modules not yet built: a module's section appears in the anchors when the module is built. The lesson plan's timeline is the exception: it always runs from 0:00 to the end, so an unbuilt module keeps its standard rows.
- Solutions fold into the challenge where they can; code that doesn't live in a notebook (a FastAPI app, a dbt project) gets a twin folder beside its starter folder with a `_solutions` suffix (`m2_fund_api/` and `m2_fund_api_solutions/`), which ships to learners like the folded solutions (user, 2026-10-16).
- Nothing is duplicated between `instructor/moduleNN-<slug>/`, `learner/moduleNN-<slug>/` and `common/data/`: the data lives once in `courseware/common/data/` ("the demo data" in `common/data/demo/`, "the challenge data" in `common/data/challenge/`). From `instructor/moduleNN-<slug>/` the demo data is `../../../../common/data/demo`; from `learner/moduleNN-<slug>/` the challenge data is `../../../../common/data/challenge` (one more `../` from a project folder inside them). Scripts resolve paths from `Path(__file__)`, never from the working directory.
- Research packs: `reference/cg-core-research/dayNN/mN-<slug>/`; verbatim copies only of Decoded-owned material, links and short quotes for everything else.

## Built outputs and sharing (user, 2026-10-16; release/latest/ in Fundamentals' shape, 2026-10-27)

This is the one statement of what the build makes and how it's shared; other skills and docs point here.

**The rule (user, 2026-10-27): Drive gets everything in its final form; reading Markdown becomes a PDF or Word file; working files ship as they are; authoring files never ship.** Reading Markdown is anything written to be read: each overview and handbook, the lesson plan (Word), both start-here pages, the release notes, each service's `INSTRUCTOR.md` and the release inventory. Working files are what learners and instructors open or run in VS Code or the containers: notebooks, project folders and their READMEs, the data (including `documents/*.md`, which the retrieval exercises read), the services and their READMEs, the dev container, and files a demo opens (`m1_checks.md`). Authoring files (`dayNN_anchors.md`, the research packs) never ship.

`scripts/build-session.sh dayNN --reviewed` builds `release/latest/` from `courseware/`, only after the user has reviewed the content (`all` builds every session; a throwaway build goes outside the repo with `--out <dir>`, into `<dir>/release/latest/`). `release/latest/` is laid out exactly like `courseware/`, the same `common/`, `unit00-programme/` and `<unit>/<session>/learner/` and `instructor/` module folders, with each reading-Markdown source replaced by its built form, so every relative path is the same in both trees. It is generated, never edited by hand, and nothing is zipped. It is tracked in git, so each release is versioned on GitHub as well as going to Google Drive; commits still happen only when the user asks. Text that ships never names `courseware/`. The build stops on a CG-access note or a `<!-- sensitive` marker in anything it ships.

```
release/
  README.md                                 # what the folder is (two short paragraphs, as Fundamentals')
  latest/                                   # the course folder, as instructors receive it
    .build-manifest.json                    #   the build's one manifest: tracked in git, never synced (check_release.py)
    RELEASE.md · RELEASE.pdf                #   the inventory (each released unit and day folder and its file count; the commit is in .last-build): the PDF goes to
                                            #   Drive, RELEASE.md stays for git and check_release.py (never synced)
    .devcontainer/                          #   the dev container VS Code reopens the course folder in
    common/                                 #   data/ · services/<name>/ · figures/<dayNN>/
    unit00-programme/
      day00-welcome/learner/module00-overview/day00_overview.pdf
      day00-welcome/instructor/module00-overview/day00_lesson_plan.docx · day00_slides.pptx · day00_slides.pdf
      learner/start-here.pdf · programme-overview.pdf · setup.pdf
      instructor/start-here.pdf · release-notes.pdf · delivery-guide.pdf · event-readiness.pdf · services/<name>/INSTRUCTOR.pdf
    <unit>/dayNN-<slug>/                    #   every unit and session folder, built or not (empty if not)
      learner/
        module00-overview/dayNN_overview.pdf
        moduleNN-<slug>/dayNN_mN_handbook.pdf · dayNN_mN_challenge.ipynb · project folder
        module99-put-it-together/dayNN_together_challenge.ipynb · catch-up folder
      instructor/
        module00-overview/dayNN_lesson_plan.docx · dayNN_slides.pptx · dayNN_slides.pdf
        moduleNN-<slug>/dayNN_mN_demo.ipynb · demo files · challenge-solution/
                        dayNN_mN_demo.pdf · dayNN_mN_challenge.pdf · dayNN_mN_challenge_solution.pdf   (review PDFs)
        module99-put-it-together/challenge-solution/ · its review PDFs
```

`dayNN_anchors.md` and every other piece of reading Markdown never ship as `.md`: `check_release.py` fails if an overview, handbook, lesson plan, start-here, release notes or `INSTRUCTOR.md` appears as Markdown, or if `RELEASE.pdf` is missing. Instructor material lives only under an `instructor/` folder (a day's, or `unit00-programme/instructor/`): a gate stops the build, and `check_release.py` fails, if anything outside one holds a lesson plan or any `.docx`, a demo, a `challenge-solution/` folder, a review PDF, release notes or an `INSTRUCTOR.pdf`, or if a learner file names one. While it writes, the build holds a `.building` lock and a finished run leaves a `.last-build` stamp (both git-ignored). A build that passes its gates writes `.build-manifest.json`; `scripts/check_release.py` and the pre-commit hook check the tree against it.

**Sharing on Google Drive.** Drive holds one copy, `release/latest/` in the shared drive's `Delivery & Workshop Materials/` (path in the git-ignored `.sync-release.env`), mirrored from `release/latest/` by `scripts/sync-release.sh` and by the git hooks from `scripts/install-sync-release.sh`. The sync leaves out the build's lock, stamp and manifest and `RELEASE.md`, so Drive holds only final forms. The Drive folders that held the release before (`courseware/`, then `ready-courseware/`) are retired by hand, and the script never touches them. Drive is for instructors; learners don't get Drive (user, 2026-10-27). Only the release owner builds and syncs: a `--reviewed` build syncs only where the Drive folder is configured, and `--no-sync` skips it. The sync deletes at most `CG_SYNC_MAX_DELETE` files a run (200 by default): look at `scripts/sync-release.sh --dry-run` first, and raise it only when every deletion is expected. Every developer installs `scripts/install-hooks.sh` once per clone: its pre-commit hook runs `scripts/check_release.py --staged` when a commit touches `release/latest/`.

**Releases** go after the user's review, by the release owner: a dated line in `courseware/unit00-programme/instructor/release-notes.md`, then a `--reviewed` build (its gates, `scripts/check_release.py`, then the sync); confirm the sync's log ends "verified: Drive matches release/latest/"; then commit `release/latest/` with its manifest. The steps are in `module-materials` → Release on Google Drive.

## Build order and outputs

- **Built outputs only after the user has reviewed the content** (user, 2026-10-15): see Built outputs and sharing above.
- **Handbook numbers come from the PDF**: `scripts/pdf-filters/handbook-section-numbers.lua` numbers each handbook's H2s 1, 2, 3 … and H3s 1.1, 1.2 …, restarting in each handbook (its H1 id ends in `-handbook`; the Summary is `{.unnumbered}`), and the PDF numbers the figures. The Markdown carries no typed numbers.
- **Code is formatted after every change** with `.venv/bin/python scripts/format_code.py <paths>`; `module-audit` runs its `--check` on the session folder.
- `learner/module00-overview/dayNN_overview.md`, `instructor/module00-overview/dayNN_lesson_plan.md` and each handbook open with exactly one H1; `module-audit` enforces that and the rest of the per-file rules.
- `releases/` is ./build-pdf's own scratch and stays ignored; `release/` (README.md and `latest/`) is the tracked release.
