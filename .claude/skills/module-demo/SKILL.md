# Module demo

Stage 2 of the seven, and the fourth step of the development flow: **handbook → lesson plan → overview → demo** → challenges. The demo section is written from the module's handbook (concepts, names, numbers) and its lesson-plan block (which beat opens which cell or file; every `### ` heading is exactly one lesson-plan row with the same title, in the same order, nothing skipped or grouped, so a section renamed or moved here is renamed or moved there too; the plan's module title equals this section's `## Module N — …` heading; user, 2026-10-27). Definition of done: `reference/subtask-descriptions.md` → **Demo**.

## Before you start

1. Read `programme-profile` (SKILL.md, `references/stack.md`, `references/layout.md`) and this session's digest.
2. Read the module's handbook and its lesson-plan block: the demo shows what the handbook explains, with the handbook's names and numbers (its concepts and real values, never its section titles or numbers), in the order the lesson plan's demo rows give, one `### ` section per beat.
3. Read the previous module's demo notebook (`instructor/moduleNN-<slug>/dayNN_mN_demo.ipynb`): the previous module's section and its artefact are what this section builds on.
4. Read [references/demo-format.md](references/demo-format.md) and `lesson-build` (anchor furniture, ship state).
5. Read `courseware-conventions/references/tech-stack.md` only for what `stack.md` does not override.
6. Look at the visual-first model, AIA `Unit 4: Deploying ML and AI Products/Session 16/demo/` (concept cards, a map of the day, Mermaid flows), for the shape, not its furniture.
7. Read `module-builder/references/session-checklist.md`, parts B to D: the rules every session is built against.

## What to build

In `courseware/<unit>/dayNN-<slug>/instructor/moduleNN-<slug>/`:

- **The module's section of the anchor** (`dayNN_mN_demo.ipynb`, or `dayNN_mN_demo.md` when the demo is a terminal workflow): `## Module N — <title>`, the 🧭 anchor and the bridge (below), the module map, the beats (no data card here: the anchor gives each dataset's card once, in its `## Setup` section at the top, with `md(nbkit.data_card("the demo data", rows))`, the Files row a list so each file and what it holds sits on its own line; a module that reads data the card doesn't cover adds it to that card), the closing (the bridge out: the last lines of the final beat, never a heading of its own; user, 2026-10-27), then the **🏆 CHALLENGE TIME box** (`md(nbkit.challenge_time_box(N, 25, "dayNN_mN_challenge.ipynb", "Module N — <challenge title>", "<one line on the task>", "<Q1>", "<Q2>", "<Q3>"))`, the tiers in a line each as the challenge's task boxes name them), and last the **Go deeper box** in its own markdown cell: `md(nbkit.go_deeper(N, "<one or two sentences: what the handbook adds, never when to read it>"))`. The challenge is built after the demo; write the box from the lesson plan's challenge block and update it when the challenge is built (`module-audit` warns while the challenge anchor does not exist yet).
- **The 🧭 anchor opens the section** (user, 2026-10-27; `programme-profile/references/conventions.md` → "Every module opens with the 🧭 anchor"). Cell order: the `## Module N` heading on its own · the anchor cell, written by `.venv/bin/python scripts/nbkit.py anchors --session <folder>` from the session's `dayNN_anchors.md` (never typed or edited in the notebook) · a bridge cell ("This builds on …" naming the concrete project, numbers and repository, plus one sentence leading into the map) · the module map cell with its bullets. Write or update the module's entry in `dayNN_anchors.md` (Title, Question, What, Why, How) before running the generator.
- **The visuals**: one brand concept card or map per beat, made by a script in `scripts/figures/dayNN/` (brand palette and Work Sans via `scripts/figures/brand.py`) into `courseware/common/figures/dayNN/`, or a Mermaid flow in the cell. Reuse a handbook figure where it already makes the point.
- **Files beside the anchor** only where a file carries the work better than a cell (a script, a config, a Dockerfile, an app): one file carries the module prefix (`m1_fund_report_reviewed.py`), several go in a named folder with its own `README.md` (`remote/`). The anchor says when to **open** the file, what to **look at**, and when to **come back**; the next cell runs or checks it.
- No placeholder sections for modules not yet built. If the anchor does not exist yet (first module of a session), create it with the title cell, the how-to-use cell and the footer, then run `scripts/nbkit.py toc --nb` on it for the 🗺️ table of contents; never type the table.

Rules that matter most:

- **The handbook appears only in the Go deeper box** (user, 2026-10-15). One box per module section, at its end, in the fixed spelling (`programme-profile/references/conventions.md`), naming "the Module N handbook" with no path, link, section title or number. Nothing else mentions the handbook: not a beat title ("· handbook 1.2"), a bullet, a code comment, an image's alt text, a module map or concept card, or a file beside the anchor. References into the handbook go stale whenever it changes; learners find topics through the PDF's contents page.
- **Visual-first** (user, 2026-10-15). The handbook carries the depth; the demo lets the instructor explain the core of each idea with visuals. After the anchor and bridge comes the module map, then each beat is one visual (a concept card or a Mermaid flow), three to five bullets, and a short code cell only when the beat runs something. Where two things are being contrasted, show them side by side in one visual. No paragraphs of explanation: if a beat needs one, it belongs in the handbook. A figure that pairs two things (a file's lines and what each makes, a step and its result) lines them up row by row, in the same order, so nothing on one side lacks its partner (S02: the Dockerfile beside the image it builds).
- **"The proper words" only where the visual doesn't show them.** When the card or diagram already labels the analogy against the technical terms, do not add a "The proper words" line under it; use the line only for a complex idea whose analogy the visual does not label.
- **Exemplar first.** After the map, the section shows the finished, useful thing running (the report, the API answering, the pipeline green), then takes it apart.
- **Every config file explained line by line.** When the demo opens a file whose lines each do a job (a Dockerfile, a pipeline YAML, a compose file), it gives a plain table in the file's own order: the line, and what it does in one short sentence, with a bullet or two on what matters most (S02 Module 6: the Dockerfile's eleven lines). Learners shouldn't have to infer a line from a comment.
- **One starting folder per module** (user, 2026-10-26). Where the module works on a project (a package, an app, a repository), it starts from its own folder beside the anchor, `mN_<project>/`, complete as the module begins, so an instructor or learner who fell behind starts the module fresh. A folder a later step continues in is named once and called the same in every file (S02: `m4_fund_report/`, `m5_fund_report/`, `m6_fund_report/`).
- **Simple, specific, defined.** The fewest files, folders, accounts, commands and steps that still show the idea (`programme-profile` CG rule 10, keep it simple). Every reference back names the file, the command and what it shows. The demo defines every term at its first use, before any shorthand for it (test-driven development (TDD) before "test-first"), because it stands without the handbook; where tests appear, it names their level (unit, integration, end-to-end smoke).
- **Connected.** It starts from the artefact the previous module left (S01: Jordan's weekly fund report) and leaves the artefact the next module needs; the lesson plan's Break row says what that is in its Transition.
- **CG workflow in the task, not as a lesson.** One AI-assisted beat per demo (after S01 M1, which teaches Copilot): plan, generate, review every generated line, validate with a deterministic check, keep or undo. Its prompt sits in the standard 🤖 COPILOT box (`md(nbkit.copilot_prompt(title, prompt, mode, model, attach=…, purpose=…, where=…))`; `programme-profile/references/conventions.md` → "The Copilot box"), whose badges name where to open Copilot (Chat view, Inline chat, Terminal chat), the mode (Ask, Plan, Agent; Chat view only), the model (Fast, Reasoning, Auto) and what to attach (an Inline chat box closes with Keep or Undo for a `.py` file in the editor, and with `then=nbkit.COPILOT_THEN_NOTEBOOK_CELL` or its own line naming **Accept and Run** for a notebook cell, where VS Code shows that button and reruns the cell; if the beat runs Ctrl+I on a file the Chat view has just edited, Keep or Undo those edits first, or Ctrl+I opens the Chat view instead), and whose prompt lines stay under about 90 characters; the anchor shows `md(nbkit.copilot_legend())` once in "How to use this notebook". Never a prompt in a blockquote, a bare fenced block or a "Choose Agent mode" sentence in place of the badges. It models the programme's way of working (`programme-profile/references/conventions.md` → "Learners direct AI and review what it wrote"): in the challenge, learners prompt Copilot to write, fix or change the code, maths included, and review it rather than typing it, so the demo shows the prompt, the review and the check it will ask of them. Link the *Working with Copilot* appendix. Catalyst where the module touches it, quoted from the handbook's `::: catalyst` box.
- **The demo data only**: `../../../../common/data/demo` from the module demo notebook; scripts resolve it from `Path(__file__)`, never from the working directory. The challenge data is for the challenge.
- **Fits the slot** (user, 2026-10-16): the demo is about 20 minutes of the module's hour, one lesson-plan row per `### ` heading (2.5 to 20 minutes, in 2.5-minute steps; user, 2026-10-27), and the challenge gets 20 to 25 (S01: demo 20, challenge 25, debrief 5, break 10). A module may run a little faster or slower with its complexity; if the demo can't be shown in about 20 minutes with time for the AI-assisted beat, it is smaller. Instructors explain less and learners spend the time in the challenge, so the demo shows the core of each idea and the handbook carries the rest. Time every beat on a real run: a step slower than its row (a push, a pipeline run, a first image build or pull) is pre-run in the break before the module and narrated live, and a note at that beat says what was pre-run; the lesson plan says so in the break row and the demo row. The images the session needs are pulled at setup.
- **Local containers.** Runs on static data in the dev container the course folder opens in and the local services in `courseware/common/services/`, so nothing waits for CG; no CG-access note, `::: blocked` callout or marked "at CG" cell, and it's "the dev container", never "the CG dev container" (`programme-profile` rule 3; user, 2026-10-16).
- **Prepared in advance and adaptable.** Everything an instructor cannot confidently produce live is in the folder; the lesson plan's demo rows name each beat with a note and a Say: what to run live, what to show and what to expect, and what to say; the instructor can skip what the room knows. The notebook carries the bullets: the plan never retells them.
- **Keys and services**: `.env.example` ships beside the anchor when needed; a missing key fails at setup naming the variable; LLM demos carry offline fixtures (`mN_fixtures/` or inside the module's named folder).
- **Boxes from `nbkit` only**: ⌨️ TERMINAL before a terminal step (`nbkit.terminal_box`), 🤖 COPILOT around every prompt (`nbkit.copilot_prompt`, with `nbkit.copilot_legend()` in "How to use this notebook"), the 🏆 CHALLENGE TIME box and the 📚 GO DEEPER box, in the spelling of `lesson-build/references/notebook-boxes.md`. Task tiers, 💭 REFLECT and 🎯 YOUR TURN boxes belong to the challenge; no polls, chat votes or timelines.
- **Self-explanatory code**: a comment on every non-trivial line, above the line it explains, or at its end when the line still fits in 88 characters; no absolute paths in any file or output.
- **Deliberately broken teaching files** are named for their job (`mN_break_it.py`), never marked or commented with their fault; `module-audit` recognises them by name and skips its path and error-handling checks for them.
- **Formatted**: after every code change run `.venv/bin/python scripts/format_code.py instructor/moduleNN-<slug>/` and finish with `--check` passing. Comments go above the code they explain wherever a comment at the end of the line would make black split it, and `scripts/format_code.py` moves them there automatically; a short end-of-line comment on a line that still fits in 88 characters may stay (user, 2026-10-16). Re-execute the anchor after black changes it.
- **Containers are services, not demo files.** They live once in `courseware/common/services/<name>/` (layout.md, Services), shared by every session's demo and challenge; never change one without rerunning `scripts/test-<service>.sh`. A new service has the full shape `programme-profile/references/layout.md` → Services gives: `service.sh`, `README.md`, `INSTRUCTOR.md`, `scripts/test-<service>.sh`, a check in `scripts/test-dev-container.sh`, and its ports in the registry before it's built.
- **Pins** (user, 2026-10-26). Every version the demo installs or quotes (a project's `requirements.txt`, a pipeline's install step, a Dockerfile's base image) matches `courseware/.devcontainer/requirements.txt` (`programme-profile/references/stack.md` → Pins; `scripts/check_pins.py`). No output shows a warning: change the pin or the code, never hide it.
- **From laptop to production** (S02 Module 6). Where a module builds something that will be deployed, the demo says in a bullet that the same artefact (the image, the tag) moves from the laptop through the pipeline to staging and production, with only settings, secrets, data, size and address changing per place; the handbook carries the depth.

## Verify

Execute the whole anchor top to bottom on a fresh kernel from `instructor/moduleNN-<slug>/` in the dev container image (the dev container, or a throwaway container from its image; nbclient, `python3` kernel), zero pre-adjustment, and re-execute after any pin change; `.venv/bin/python` is for quick checks while building, never for the shipped outputs; run every file the anchor opens exactly as the anchor says. Every number in the anchor's prose matches the handbook's worked example; if the run disagrees, the handbook is fixed first and the change flows down. Every served app: boot it, hit `/health` and one real route on the registered port, stop it. Every LLM path: once with a key, once with fixtures. Every service the section uses: its `scripts/test-<service>.sh` passes and `scripts/test-dev-container.sh` starts it from inside. Then `module-audit` on the session folder.

## Ship

Executed notebook with sequential counts from a single top-to-bottom run, title and footer cells, the 🗺️ table of contents rebuilt after the section was added (`scripts/nbkit.py toc --nb instructor/moduleNN-<slug>/dayNN_mN_demo.ipynb --check` passes), every prompt in a 🤖 COPILOT box and the Copilot legend in "How to use this notebook", a module map and one visual per beat, the 🏆 CHALLENGE TIME box then one Go deeper box closing the section and no other mention of the handbook, every card's script in `scripts/figures/dayNN/`, code formatted (`format_code.py --check` passes), no absolute paths, keys or warnings in outputs, `scripts/test-dev-container.sh` and the services' tests passing, no litter. The session's handover checks are the session checklist's part E (`scripts/check-session.sh dayNN`). If the run changes a number or a name, mirror it upstream into the handbook and the lesson-plan block in the same pass. Register any new port in `programme-profile/references/stack.md`. Hand the artefact the section ends with to `module-challenge`.
