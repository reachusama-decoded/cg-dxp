# Markdown conventions for CG Core

Adopted 2026-10-13 from the DataCreators v4 dialect as the working standard until MJB's sample module and Pandoc conventions arrive; reshaped 2026-10-15 for the session folder of overview, lesson plan, handbooks and anchors (`programme-profile/references/layout.md`). When MJB's conventions arrive, diff them against this file, update it, and note the change in `programme-profile/references/conventions.md`.

## Document structure

- **One H1 per file** for `learner/module00-overview/dayNN_overview.md`, `instructor/module00-overview/dayNN_lesson_plan.md` and each `learner/moduleNN-<slug>/dayNN_mN_handbook.md`. Each file with an H1 builds its own PDF (`learner/module00-overview/dayNN_overview.pdf`, `learner/moduleNN-<slug>/dayNN_mN_handbook.pdf`); the lesson plan is built to Word only (`instructor/module00-overview/dayNN_lesson_plan.docx`, by `scripts/docx/build_lesson_plan.js`), so there is no lesson-plan PDF.
- Explicit ids on every heading that anything links to. Overview: `{#sNN}`, `{#dayNN-questions}`, `{#dayNN-outcomes}`, `{#dayNN-before}` with `{#dayNN-contents}`, `{#dayNN-setup}` and `{#dayNN-self-check}` under it, `{#dayNN-agenda}`, `{#dayNN-challenges}`, `{#dayNN-data}`. Handbook: `{#dayNN-mN-handbook}` on the H1 (the PDF's section-numbering filter keys on the `-handbook` ending), `{#dayNN-mN-covers .unnumbered}` on What this handbook covers, `{#dayNN-mN-k}` on its k-th H2, `{#dayNN-mN-summary .unnumbered}` on the Summary. Lesson plan: `{#dayNN-welcome}`, `{#dayNN-mN}` on each module block, `{#dayNN-open}` on open challenge time and `{#dayNN-wrapup}`, then `{#dayNN-mN-reference}` and `{#dayNN-together-reference}` on the reference sections; there is no put-it-together block.
- Links between the overview and the handbooks use the H1 id (`[the Module 1 handbook](#day01-m1-handbook)`); the `book-links.lua` filter resolves them in the bundle. The overview and the lesson plan point to a handbook as a whole, never to a section's id, number or title. The overview (in "Before you start") links the learners' `challenge/` by relative path and never anything under `instructor/`; the lesson plan names `demo/`, `challenge-solution/` and the learners' `challenge/`; a handbook links none of them. These are navigation; sources are never linked in overview or handbook prose (Prose rules below).
- Front matter: none. `builder.toml` carries the title block; `scripts/build-session.sh` sets the session subtitle from the overview's H1.
- Tables: pipe tables with a header row. No HTML tables, no merged cells. A table wider than five columns becomes two tables.
- Code: fenced with a language (`python`, `bash`, `sql`, `yaml`, `text` for output, and for a Copilot prompt inside its `::: copilot` div, never a bare one: "Copilot prompts" below). Shell blocks show the command and, in a separate `text` block, the real output from a run with the project venv or the dev container. Never `$` prompts inside the block.
- Mermaid: ```` ```{.mermaid height="0.32" fontsize="18"} ```` … ```` ``` ````. Plain nodes, `-->`, `<br>`, `style`. No `~~~`, no `direction` in subgraphs, no `timeline`. `&amp;` for ampersands. Prefer a Python figure when the diagram is quantitative.
- HTML comments carry no markers. No `<!-- sensitive: … -->` marker (user, 2026-10-19): write to `programme-profile` CG rule 2 (pros and cons, never limitations) the first time; `module-audit` reports any marker as an error. No `<!-- blocked: … -->` marker: CG Core content carries no CG-access notes (`programme-profile` rule 3; user, 2026-10-16). HTML comments never reach the PDF (2026-10-16): `scripts/pdf-filters/strip-html-comments.lua`, first in `builder.toml`'s local filters, drops every block or inline that is only comments, so a comment between a heading and its text never splits them across a page. The one comment the build reads is a `<!-- caption: … -->` straight after a diagram block (```` ```mermaid ````, `d2`, `dot` or `diagram-py`), which becomes the figure's caption; anywhere else that comment is dropped too. So never put anything that should print in a comment.

## Handbooks (L6 style)

Model: `reference/L6-source content/M09 Deep Learning, LLMs, and Generative AI  - Handbook (WIP).md`.

- `# <Module title> {#dayNN-mN-handbook}`, a short introduction (below), then plain H2 and H3 headings with **no typed numbers** (user, 2026-10-15): `## Notebooks, scripts and how Python runs your code`, never `## 1.2 …`. When the PDF is built, `scripts/pdf-filters/handbook-section-numbers.lua` numbers the H2s 1, 2, 3 … and the H3s 1.1, 1.2 …, restarting in each handbook; headings inside callouts and `{.unnumbered}` headings are left alone. The last section is `## Summary {#dayNN-mN-summary .unnumbered}`, followed only by the optional appendix (below).
- **The opening and the persona card** (user, 2026-10-19), so learners know what to expect: under the H1, the breadcrumb and the italic tagline, the intro paragraph says what the handbook covers ("This handbook covers …") and nothing else, then, straight after it, each handbook's own card: `nbkit.persona_card_pdf_md(rows)` gives "#### Persona card — Jordan Mensah" and the overview's grid table, with five fields in order. **Who**: Jordan Mensah (they/them) works with code and data at Harbourline Asset Management, an invented UK asset manager. **This module**: where Jordan's work stands as the module begins, true to what the handbook then shows. **What gets in the way**: the problem the module solves for Jordan. **By the end**: what the work becomes by the end of the module. **The examples**: Harbourline, its funds and every number are invented; every output shown comes from a real run with Python and pandas, never with a version number ("Python 3.13", "pandas 2.3"). Each cell a line or two, in Decoded's plain voice, consistent with the overview's card and `programme-profile` CG rule 2. Who Jordan is, the invented data and the real runs live in the card, never in the intro paragraph. After the card comes the module's 🧭 anchor (generated from `dayNN_anchors.md`, never typed; the card stays as it is), then the useful output the handbook starts from, if any, then `## What this handbook covers {#dayNN-mN-covers .unnumbered}` (user, 2026-10-19): a heading, unnumbered like the Summary, never a bold line. The card's words count towards the word range. `module-audit` warns on a missing card, one not straight after the intro paragraph, fields out of order and a version number in it. The card looks the same in every PDF: see "The persona card's design" under Overview.
- Each H2 section ends with `### Optional further reading` (in the PDF, by `scripts/pdf-filters/further-reading.lua`, each item shows its type label, then the link's web address in place of the title and source, clickable, and the description after " — " on its own indented line beneath; write the full Markdown item, "**Type:** [*Title*](url) by Source — what it adds.", and the filter does the rest): two to five verified links from the module's `references.md`, one line each on what it adds. This list is the only place a handbook links or names a source; the prose above it carries no links, citations or source asides.
- Figures: the image on its own line, introduced by the sentence above it; its description is the caption, and there is no separate caption line:

  ```markdown
  The chart below ranks the eight UK Equity share classes by one-year return.

  ![One-year return for the eight UK Equity share classes in the demo data, highest first.](../../../../common/figures/day01/m1-one-year-return.png){width=90%}
  ```

  A Mermaid figure's caption is an HTML comment straight after its closing fence: `<!-- caption: "The four moves with Copilot." -->`. The PDF numbers the figures; the Markdown never types "Figure 1.3", and prose never cites a figure or a section by number ("the chart below", "the four moves"). Never a bare image under a heading.
- Catalyst appears only inside `::: catalyst` boxes; the prose around them stands on its own.
- Worked examples run on the demo data with Jordan, and every number and output is pasted from a real run in the dev container image, never edited by hand, and re-run after any pin change (`.venv/bin/python` is for quick checks only, never for a quoted output). A code block that reads data shows the path as the reader would type it from their own folder; no absolute home paths.
- Learner words (code excluded): 3,000 to 12,000, aiming for about 7,000; past 7,000 only for topic knowledge (user, 2026-10-26). Delivery detail goes to the lesson plan; truly optional depth to the appendix.
- **The optional appendix** (S02 M6): `## Going further with <topic> {#dayNN-mN-appendix .unnumbered}` after the Summary, opening with "Nothing in this appendix is needed for working through the module, for the exercises or for the outcomes.", lettered `### A. … {.unnumbered}` subsections, and `### Further reading for the appendix {.unnumbered}`. Nothing in the main text depends on it.
- Self-contained: no mention of demos, challenges, the session, the agenda, setup, instructors or Asana; no links into `instructor/` or a challenge notebook; never "in the next module" or "Module N covers". A handbook may build on concepts from earlier handbooks, named by the concept ("a script that recomputes its report from the data"), not by module number.
- Where text discusses tools, platforms or ways of working, it compares them with their pros and cons and says what each is good for, never leading with a tool's limitations, in table headings too ("Good for", "Trade-offs"); review and checks are good practice every change gets (`programme-profile` CG rule 2).

## Overview

- **The order** (user, 2026-10-19): the opening, one or two sentences that introduce Jordan ("Every session follows **Jordan Mensah**, …"); the persona card; the session in a paragraph, tied to Jordan's report; how the day runs, open challenge time optional; `## The questions you'll answer`; `## What you will be able to do`; `## Before you start` (a line on what it pairs with and assumes, then `### What's in this session`, a table whose handbook rows read "Module N handbook: concepts in depth" (no demo row: demos are instructor-only, user, 2026-10-27); `### Set up at the start of the day`, with the "**Services this session uses:**" line and a `::: workflow` of steps done as learners arrive; `### What you already know`); `## Agenda` (its one-line lead, then the agenda table); `### How the challenges work` (the outlined tier table with its badges); `## The data`. The shape, with every id, is in `lesson-build` SKILL.md → File shapes.
- A persona card straight after the opening paragraph (user, 2026-10-16), so learners see themselves in the session: `nbkit.persona_card_pdf_md(rows)` gives "#### Persona card — Jordan Mensah" and a grid table like the data cards, with five fields in order. **Who**: Jordan Mensah (they/them) works with code and data at Harbourline Asset Management, an invented UK asset manager, and is moving into data and AI engineering; no job title. **This session**: Jordan's situation at this point in the programme, in a line. **What gets in the way**: the problem the session solves, as Jordan meets it. **By the end**: what Jordan has, from the session's artefacts. **You**: what the learner does, on the challenge data. One card per overview; each handbook has its own persona card (Handbooks above, user, 2026-10-19), and the anchors and the lesson plan have none. Jordan is the thread, not the hero.
- **The 🧭 anchor divs** (user, 2026-10-27; `programme-profile/references/conventions.md` → "Every module opens with the 🧭 anchor"): the overview carries none, the day's or a module's (user, 2026-10-27: the day-level anchor is retired, and `nbkit.py anchors` removes any old one); each handbook one after its persona card; the lesson plan one at the top of each module's section. They are written by `nbkit.py anchors` from `dayNN_anchors.md`, never by hand, and drawn by `scripts/pdf-filters/module-anchor.lua` and the Word builder.
- **The persona card's design** (user, 2026-10-19): one branded design wherever a persona card appears, the overview and every handbook alike, so it stands out from the ordinary tables around it. `scripts/pdf-filters/persona-card.lua` (registered in `builder.toml`) turns the "#### Persona card — <name>" heading and the table straight after it into one box in the 🤖 COPILOT box's family: a brand-yellow header bar (`#FEF800`, the cover logo's `decodedyellow`) reading "PERSONA — <name>" (no 👤: the PDF fonts can't print it), then each row's label on pale yellow (`#FFFDCC`) beside its value on white, in a thin dark frame (`#434343`) with thin rules between the rows. Long values wrap; the card is never split across pages; the heading is never numbered and never in the contents. So write the card only with `nbkit.persona_card_pdf_md`: the heading must start "Persona card — ", with nothing between it and its two-column table, and never style a card by hand or give it a heading of another level. Notebooks carry no persona card; if one ever does, it uses `nbkit.persona_card_html`, the notebook twin in the same colours.
- **Outlined tables** (user, 2026-10-19): the overview's agenda table and its tier table under "How the challenges work" each sit in a `::: {.outlined}` div (the fence straight above the table, `:::` straight below), which `scripts/pdf-filters/outlined-table.lua` draws in the cards' family: a thin `#434343` frame, a header row shaded `#F3F3F3` in bold, thin rules between rows and columns, the first column bold, wrapping cells, a row never split across pages (a long table breaks between rows and repeats its header); tier badges inside stay badges. Use it only for those tables; every other table stays a plain house table.
- **The data card's design** (user, 2026-10-19): the persona card's design in blue, so the two cards read as one family. The same filter draws every "#### Data card — <name>" heading (`nbkit.data_card_pdf_md`) and the grid table straight after it with the same drawing function, frame, rules, fonts, spacing and keep-together, only the palette and title changed: a header bar in the Copilot box's MODEL badge blue (`#C9DAF8`) reading "DATA — <name>" (no 🗂️), each label on a pale tint of it (`#E4EDFC`, half-way to white, because a 20% tint of so pale a blue is all but white) beside its value on white, in the thin `#434343` frame. The Files row keeps one file per line as a bullet list. Notebooks show the same card as HTML, `nbkit.data_card` (header bar "🗂️ DATA — <name>"), built by the one helper `persona_card_html` uses, so the two can't drift; `scripts/nbkit.py selftest` checks both cards' HTML colours against the filter's. Never style a data card by hand.
- Outcomes live here only: stem "By the end of this session you will be able to:", about five bullets, bold leading verb, behaviour + standard + condition, with no trailing module tag (user, 2026-10-15; the lesson plan maps outcomes and questions to modules). Copy them verbatim from `internal-programme-overview.md` §6. The `::: session` questions and the "what you already know" self-check are untagged too; the lead-in may say that each module answers some of the questions. The self-check has at most three yes-or-no questions, one per module in module order, each about the prior knowledge that most changes how fast and how deep that module goes (S01: Python functions; commands on a remote machine; a Python environment others can recreate), and the lesson plan's welcome (its *What you will be able to do* row) says which question paces which module and what to adjust. Observable verbs only: describe, explain, list, compare and contrast, write, design, annotate, create, discuss, analyse, request, refine.
- The agenda carries no times or minutes (they live in the lesson plan); its Welcome row reads `| Welcome | Meet and greet, Jordan and the day, what you will be able to do | One thing you want from today |` (user, 2026-10-27), each module row names the module by its canonical title, word for word, and the rows end with "Open challenge time (optional)", the Closing debrief and the Wrap-up; rows for modules not yet built are left out.
- No `::: notes`, no instructor text, no time-of-day rhetoric.

## Copilot prompts (every file; user, 2026-10-16)

Wherever learners or instructors are told to prompt Copilot, the prompt sits in the standard 🤖 COPILOT box: what it is, when to use it and how to choose the settings are in `programme-profile/references/conventions.md` → "The Copilot box". Never a blockquote, a prose label such as "(Copilot Chat, Ask mode)" or a bare fenced block.

- **Markdown that becomes a PDF or the Word lesson plan** (handbooks, the overview, the lesson plan): a `::: copilot` div around a ```` ```text ```` block. `scripts/pdf-filters/copilot-box.lua` draws the header (without the 🤖, which the PDF fonts can't print), the badges, the prompt and the closing line, and `scripts/docx/build_lesson_plan.js` draws the same in the Word lesson plan.

  ````markdown
  ::: {.copilot title="Turn the cells into a script" where="Chat view" mode="Agent" model="Fast" attach="#report.ipynb"}
  ```text
  Turn the cells in #report.ipynb into a new script called fund_report.py.
  Context: the data is in ../../../../common/data/demo/ (funds.csv, fund_nav_daily.parquet).
  Check: python fund_report.py prints the same 8 rows as the notebook.
  ```
  :::
  ````

  `title` (the job in a few words), `where` (Chat view, Inline chat or Terminal chat: the surface to open) and `model` (Fast, Reasoning or Auto) are required, and so is `mode` (Ask, Plan or Agent) with `where="Chat view"`, the only surface with a mode; Inline chat and Terminal chat take no mode (`::: {.copilot title="Find the biggest files" where="Terminal chat" model="Fast"}`). A div with no `where` draws as Chat view, and the audit warns; `mode=""` counts as no mode, and an empty or unknown mode warns and is left out, never drawn as a badge (the PDF filter and the Word builder agree). `attach` only when the prompt needs context: `#<file>`, `selection`, `#codebase`, `#terminalLastCommand` or `#terminalSelection`, several separated by spaces; an Inline chat div takes no `selection`, because Inline chat works on the selected lines already, and its purpose paragraph says which lines to select. The closing line follows the surface: Chat view's by mode, Inline chat's "read the change in the editor, choose Keep or Undo, and run the check" (a `.py` file in the editor; Inline chat in a notebook cell shows **Accept and Run** instead, so a notebook box sets its own line, and a handbook div about a notebook cell does the same with `then=`), Terminal chat's "choose Insert, not Run: read the command, press Enter, and check what it printed". A short paragraph before the code block inside the div is the box's one-line purpose; `then="…"` replaces the closing line and `then="none"` leaves it out. The closing line already says what to do with the answer, so the text after the div moves on rather than repeating it.
- **Prompt lines** stay under about 90 characters so they don't wrap in the PDF: one line per part of a brief, split where a part runs long.
- **Anchors** (notebooks and Markdown anchors): `md(nbkit.copilot_prompt(title, prompt, mode, model, attach=None, purpose=None, then=None, where="Chat view"))` (`mode=None` with Inline chat or Terminal chat), or its `copilot_prompt_html` string pasted as a block in a Markdown anchor, and the Copilot settings legend (`nbkit.copilot_legend()`) once in "How to use this notebook" or the cell after it. Folded solutions give their model prompt with `nbkit.copilot_solution(prompt, change, check, mode=…, model=…, attach=…, where=…)`, which prints the same badges and text block.
- `module-audit` warns on a fenced block that reads as a prompt outside the box, an incomplete `::: copilot` div (one with no `where` included), a badge value outside the vocabulary, a blockquote prompt in a folded solution, an anchor with Copilot boxes but no legend, a `then=` that doesn't fit its surface and Accept or Discard named as Inline chat's buttons (**Accept and Run**, a notebook cell's button, passes).

## Prose rules (handbook and overview; user, 2026-10-15)

- **Connected paragraphs.** Each paragraph develops one idea over several sentences (usually three to six), and a transition carries the reader into the next paragraph. No runs of one- and two-sentence paragraphs: merge them into the paragraph whose idea they serve, or turn a list of parallel items into a real list. This overrides Decoded's short-paragraph rule for Core handbooks and the overview's prose. A flow or comparison still becomes a figure or a table.
- **No in-line references.** No links, citations or asides such as "(VS Code docs, …)" or "(see the pandas guide)" in a paragraph, list item or caption. Sources appear only in the section's "Optional further reading" list. Paraphrase documentation in your own words rather than quoting it; the `::: catalyst` box is the one quotation, because CG guidance is never paraphrased.
- **"The proper words" only where the visual doesn't show them.** When a figure or diagram already labels the analogy against the technical terms, do not repeat the mapping as a "The proper words" line under it. Keep the line for a complex idea whose analogy the visual does not label.
- **No figure or section numbers in prose.** The PDF numbers them; the text says "the chart below" or names the idea.
- **Spacing is the build's, never the Markdown's** (user, 2026-10-19): every house PDF gets the same room round its text from `scripts/pdf-headers/spacing.tex` (more between paragraphs, clearly more above and below code blocks, figures, lists and boxes, a code block and its output kept close as one pair, a figure that just misses the page foot drawn a little smaller, down to 75%, rather than leaving a gap). So never add blank-line padding, `\vspace`, `<br>` or empty paragraphs to open a page up: change the header, which changes every PDF alike.
- **A command and its output stay on one page** (user, 2026-10-19): two code blocks with nothing between them, the command and then its `text` output, are a pair, and `scripts/pdf-filters/code-with-output.lua` never lets the page break between them; a pair of up to 20 lines together doesn't break at all, and a longer one may break inside a block, never with the command alone at a page foot and its output overleaf. So write the output straight after its command, with no sentence between, and never move a block or pad the text to fix a page break.
- Every rule says why. Every tool says what it lets you do before what it is.
- A "Jordan" beat is one or two sentences, in the present tense, Jordan they/them, at Harbourline Asset Management, woven into a paragraph rather than standing alone.
- No later module or session named as where something is taught: use a trigger ("as soon as the script has to run somewhere else").
- **Be specific** (user, 2026-10-27; Decoded-wide, `courseware-conventions`). A reference back names the file, the command and what it shows, never "a check" or "a saved copy".
- **Define first.** Name and define each term at its first use, before any shorthand (TDD before "test-first"); where tests appear, name their level (unit, integration, end-to-end smoke) and what each is good for.
- **Keep it simple.** The fewest steps and moving parts that still teach the idea.
- The lesson plan keeps short spoken lines and the demo keeps bullets; these prose rules are for reading text.

## Anchor notebooks and Markdown anchors

- **Demo notebook (visual-first), one per module:** nbkit's short, identical header (title, table of contents, two lines of how to use, the Copilot legend, setup cell, data card), the module's `## Module N — <title>` section, footer. Each module section opens with four cells: the heading, the 🧭 anchor (generated by `scripts/nbkit.py anchors`), a bridge ("This builds on …", naming the project, numbers and repository, plus one line into the map), then the module map. Each beat is one visual, three to five bullets, and a short code cell only when the beat runs something. A visual is a brand concept card or map from `courseware/common/figures/dayNN/` (`<img src="../../../../common/figures/day01/m1-card-kernel.png" width="900"/>`, made by `scripts/figures/dayNN/`) or a Mermaid flow in a ```` ```mermaid ```` fence (plain nodes, `-->`, `<br>`, `&amp;`; the same safety rules as above). Contrasts are shown side by side in one visual. No "The proper words" line under a visual that already labels the mapping. A markdown cell says **open** `<file>`, **look at** `<what>`, **come back**, before the code cell that runs or checks the file. A config file opened this way (a Dockerfile, a pipeline file) gets a plain line-by-line table in the file's own order. A figure whose rows explain something lines them up with it. A ⌨️ TERMINAL box (`nbkit.terminal_box`) precedes each terminal step, and the AI-assisted beat's prompt sits in a 🤖 COPILOT box (`nbkit.copilot_prompt`), with the Copilot settings legend (`nbkit.copilot_legend()`) in "How to use this notebook". Each module section ends with the 🏆 CHALLENGE TIME box (`nbkit.challenge_time_box`) and then the Go deeper box. Executed, sequential counts.
- **Challenge notebook, one per module:** the same short header, plus the difficulty legend (and the Copilot settings legend) in "How to use this notebook" and a setup cell of its own; per task, the heading, 🧭 anchor and bridge cells (the anchor identical to the demo's, a recap), then one recap visual of the demo section it follows (reused from `courseware/common/figures/dayNN/`, or the demo's Mermaid flow), then AIA's box set built with `nbkit` (exact HTML in [notebook-boxes.md](notebook-boxes.md)): one ⚡ task box per tier (Q1 · CORE first in every section, Q2 · STRETCH, Q3 · BONUS not expected), the starting code with its planted fault, a 🤖 COPILOT box wherever a task hands learners a prompt, ⌨️ TERMINAL boxes, 🎯 YOUR TURN boxes for no-code tasks, and a 💭 REFLECT box with the solution folded under it:

  ````markdown
  <div style="border:2px solid #F8DB59; border-radius:8px; margin:10px 0;">
  <div style="background:#FFF2CC; color:#000; padding:8px 14px; font-weight:bold;">💭 REFLECT &nbsp;—&nbsp; before you open the solution</div>
  <div style="background:#fffef5; padding:12px 14px; color:#1a1a1a;">Which line would you change if the report had to cover two categories?</div></div>

  <details>
  <summary><strong>Solution — attempt before opening</strong></summary>

  **A prompt that works:** ‹the WHERE, MODE, MODEL and ATTACH badges: nbkit.copilot_badges_html("Agent", "Fast", "#fund_report.py")›

  ```text
  #fund_report.py Make the category an argument, with Global Equity as the default.
  Change nothing else.
  ```

  **The change a good answer makes:**

  ```python
  # the fixed code, with comments on the decisions
  ```

  **The check that proves it:** run it on two categories and compare the row counts.

  **Reflect — answer:** Two or three sentences.

  </details>
  ````

  Every solution sits inside a `<details>` block straight after a 💭 REFLECT box, built with `nbkit.reflect_solution(question, nbkit.copilot_solution(prompt, change, check, mode=…, model=…, attach=…, where=…), answer)`, so its model prompt carries the Copilot box's badges and sits in a ```` ```text ```` block (never a blockquote); no solution heading or code cell outside one. Learners prompt Copilot to write, fix or change the code and review what it wrote (`programme-profile/references/conventions.md` → "Learners direct AI and review what it wrote"): code cells hold complete starting code, a `___` only records an observation or decision in markdown or a string, and there are no `# TODO` gaps, "Step N" headings or "fill the gaps". The challenge stands alone: no path into `instructor/` and no demo file, anchor or variable; services in `courseware/common/services/` may be used. A challenge notebook ships without outputs.
