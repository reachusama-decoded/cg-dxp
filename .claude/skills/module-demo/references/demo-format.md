# Demo format

One demo notebook per module (user, 2026-10-27), `instructor/moduleNN-<slug>/dayNN_mN_demo.ipynb` (or `.md`), for instructors only, plus the files it opens, all inside the module's folder. Each module notebook stands alone: it opens with the short, identical header nbkit generates (title, table of contents, two lines of how to use, the Copilot legend, one setup cell and the data card), then the module section. The anchor carries the flow; the files carry the work that is better read as a file. The demo is **visual-first** (user, 2026-10-15): the handbook carries the depth, and the demo lets the instructor explain the core of each idea with visuals. Model: AIA `Unit 4: Deploying ML and AI Products/Session 16/demo/`.

## The folder

```
instructor/moduleNN-<slug>/     # e.g. instructor/module04-unit-testing-pytest/ (no demo/ subfolder)
  dayNN_mN_demo.ipynb           # the module's demo notebook (day02_m4_demo.ipynb)
  m1_fund_report_reviewed.py    # one file a module adds: module prefix
  mN_<what>/                    # several files a module adds: a named folder with its own README.md
  mN_<project>/                 # the module's project folder, beside the notebook that uses it (S02: m4_fund_report/)
  .env.example                  # only when a module needs a key
```

## Module demo notebook

- **Cell 1**: the Decoded title cell, `nbkit.title_cell("<session title>", nbkit.breadcrumb(<unit>, "<unit title>", NN, "demo notebook"))` (no version line).
- **Cell 2**: the 🗺️ table of contents, its own cell (id `toc`), generated by `scripts/nbkit.py toc --nb instructor/moduleNN-<slug>/dayNN_mN_demo.ipynb` after `write()` and never typed: a row per `## ` section from How to use on, each linking to the anchor line nbkit puts at the top of that heading cell, and listing the section's `### ` beats, then Challenge time. It names no minutes and never the handbook (`lesson-build/references/notebook-boxes.md` → "Table of contents").
- **Cell 3**: the short, identical how to use (two lines, generated by nbkit): run it top to bottom; which files sit beside it; the data is the demo data at `../../../../common/data/demo`. Then the Copilot settings legend, `md(nbkit.copilot_legend())` (in this cell or the next), whenever the notebook has a 🤖 COPILOT box, so each badge is explained once.
- **Cell 4 on**: the setup cell and the demo data card, then the module section, in order:
  1. `## Module N — <title>`, alone in its heading cell.
  2. **The 🧭 anchor**, its own cell, generated from `dayNN_anchors.md` by `scripts/nbkit.py anchors --session <folder>` (never typed).
  3. **The bridge**, its own cell: "This builds on …" naming the concrete project, numbers and repository the module starts from, then one sentence leading into the map.
  4. **The module map**, its own cell: one visual of the module's beats and the artefact it changes (a card from `courseware/common/figures/dayNN/`, or a Mermaid flow), with its bullets.
  5. The exemplar: the useful output first.
  6. **The beats**, each in this shape, the concepts' names and the real numbers as in the handbook (never its section titles or numbers):

     ````markdown
     ### <Beat title>

     <img src="../../../../common/figures/day01/m1-card-kernel.png" width="900"/>

     - <three to five bullets: the core of the idea, what to notice, why it matters to Jordan's report>
     ````

     then a short, commented code cell only when the beat runs something. One visual per beat: a brand concept card in the Decoded palette, made by `scripts/figures/dayNN/mN_card_<what>.py` into `courseware/common/figures/dayNN/mN-card-<what>.png`, or a Mermaid flow in a ```` ```mermaid ```` fence (plain nodes, `-->`, `<br>`, `&amp;`; no `~~~`, no `direction` in subgraphs, no `timeline`). Where two things are contrasted (notebook and script, local and remote), one side-by-side visual. Bullets, not paragraphs: depth lives in the handbook. No "The proper words" line under a visual that already labels the mapping; keep it for a complex idea whose analogy the visual does not label.
  7. Where a file beside the anchor carries the work, a markdown cell in this shape, then the cell that runs or checks it:

     ```markdown
     **Open** `m1_fund_report_reviewed.py`. **Look at** the `main()` function and the path line at the top: the script finds the data from its own location. **Come back** here and run the next cell.
     ```

  8. The AI-assisted beat (after S01 M1): the prompt, the review of every generated line, the check, and Keep or Undo, with its own visual like any other beat. The prompt sits in the standard 🤖 COPILOT box, never in a blockquote or a bare fenced block (`programme-profile/references/conventions.md` → "The Copilot box"):

     ```python
     # title: the job in a few words; prompt: the brief, one line per part, under ~90 chars
     # mode: Ask to understand, Plan for a bigger change, Agent to create or change files
     # model: Fast for quick edits, Reasoning for multi-step work, Auto where Copilot may pick
     # attach: only when the prompt needs context (#<file>, selection, #codebase, #terminalLastCommand);
     #   never selection in Inline chat, which works on the selected lines already
     # where: Chat view (default; mode required), Inline chat for one change to selected code,
     #   Terminal chat for a shell command (both with mode=None)
     # then: Inline chat on a .py file keeps the default Keep or Undo line; Inline chat in a notebook cell
     #   passes then=nbkit.COPILOT_THEN_NOTEBOOK_CELL (VS Code shows Accept and Run there, which reruns the cell)
     md(
         nbkit.copilot_prompt(
             "Turn the cells into a script",
             prompt,
             mode="Agent",
             model="Fast",
             attach="#day01_demo.ipynb",
             purpose="One line on what the prompt is for.",
         )
     )
     ```

     The box ends with the mode's closing line (Agent: read every line, Keep or Undo, run the check), so the bullets after it go straight to the review. Any `/explain` the instructor shows gets its own box (Ask, Fast, `selection`). It models what the challenge asks of learners, who direct Copilot and review what it wrote rather than typing code (`programme-profile/references/conventions.md` → "Learners direct AI and review what it wrote").
  9. The closing: the last lines of the final beat, never a heading of its own (user, 2026-10-27): what the artefact is now, and the trigger the next module answers ("this only runs on your laptop so far"). Every `### ` heading above it is one lesson-plan row with the same title, in the same order.
  10. **The 🏆 CHALLENGE TIME box**, in its own markdown cell just before the Go deeper box: `md(nbkit.challenge_time_box(N, 25, "dayNN_mN_challenge.ipynb", "Module N — <challenge title>", "<one line on the task>", "<Q1>", "<Q2>", "<Q3>"))`. It links the learners' challenge anchor, `../../learner/moduleNN-<slug>/dayNN_mN_challenge.ipynb` (the same path in `courseware/` and `release/latest/`), at the module's section, gives each tier in a line, and ends by telling learners to start at Q1 and go as far as they can, with Q3 not expected (AIA's dark box, exact HTML and wording in `lesson-build/references/notebook-boxes.md`). The minutes are the module's challenge time in the lesson plan, its two challenge rows together: about 20 to 25 (S01: 25, as 15 + 10), never a split per tier. Put it together isn't in any CHALLENGE TIME box: it is the optional stretch in the session's open challenge time.
  11. **The Go deeper box**, last in the section, in its own markdown cell: `md(nbkit.go_deeper(N, body))`. The spelling is fixed (AIA's demos); only the body changes:

     ```html
     <div style="border:2px solid #F8DB59; border-radius:8px; margin:10px 0;">
     <div style="background:#F8DB59; color:#000; padding:8px 14px; font-weight:bold;">📚 GO DEEPER &nbsp;—&nbsp; the Module N handbook</div>
     <div style="background:#fffef5; padding:12px 14px; color:#1a1a1a;">One or two sentences: what the handbook adds (the full explanation, more worked examples, further reading).</div></div>
     ```

     The body is one or two sentences on what the handbook adds (the full explanation, more worked examples, further reading): no path, no link, no section title or number. **It is the only place the demo mentions the handbook**: beat titles, bullets, code comments, alt text, the module map, the concept cards and the files beside the anchor never do.
- **Setup cells are minimal**: imports, `load_dotenv()` when a key is needed, a file check with a clear message; nothing starts.
- **Servers** start in their own clearly headed cell inside the section that uses them and stop at the end of that section.
- A 👀 line next to any cell that changes something outside the notebook (a file, a page, a container), saying where to look.
- A ⌨️ TERMINAL box (`nbkit.terminal_box(title, body, commands)`) before every step the instructor runs in a terminal, with the commands in the same cell.
- **Last cell**: the footer.
- Shipped executed in the dev container image, top to bottom, sequential counts, no absolute paths, keys, warnings or learner traces in outputs.
- Boxes come from `nbkit` only, in AIA's spelling: ⌨️ TERMINAL, 🤖 COPILOT (with its legend in cell 2), 🏆 CHALLENGE TIME and 📚 GO DEEPER. Task tiers, 💭 REFLECT and 🎯 YOUR TURN boxes belong to the challenge; no polls, chat votes or timelines.

## Markdown anchor (terminal workflows)

`instructor/moduleNN-<slug>/dayNN_mN_demo.md`: the same order and the same visual-first beats (module map, one visual and three to five bullets per beat), an H1 title, `## Module N — <title>` sections each ending with the challenge-time box and then the Go deeper box, each pasted as its own block (`nbkit.challenge_time_box_html(…)`, `nbkit.go_deeper_html(N, body)`), every prompt pasted as `nbkit.copilot_prompt_html(…)` with `nbkit.copilot_legend_html()` under "How to use this notebook", one fenced `bash` block per step with the real output in a `text` block under it. Every container, dbt and Airflow command carries a comment per flag. Use it when the workflow *is* the lesson (CLI, Git, Docker, dbt, Airflow) and a notebook would hide it.

## Concept cards

- One script per card in `scripts/figures/dayNN/` (`mN_card_<what>.py`, or `mN_map.py` for the module map), using `scripts/figures/brand.py` for the palette and Work Sans, writing `courseware/common/figures/dayNN/mN-card-<what>.png` (or `mN-map.png`). A card is a picture with short labels, not a paragraph in a box, and never names the handbook or a handbook section.
- The challenge reuses a card or the map as its recap visual; the handbook may reuse a card as a captioned figure.
- Eyeball every card at the width the anchor shows it (900 px).

## Files beside the anchor

- Scripts resolve paths from `Path(__file__)` (`DATA = Path(__file__).resolve().parents[4] / "common" / "data" / "demo"` for a script directly in the module folder, `parents[5]` for one inside a project folder), so they run from any working directory, and let errors fail loud.
- A file broken on purpose for teaching is named for its job (`mN_break_it.py`) and carries no comment or marker that gives its fault away; `module-audit` recognises it by name (`PLANTED_FAULTS`) and skips its path and error-handling checks.
- Formatted with `scripts/format_code.py` (isort, black); comments that would split a line go above the code (the formatter moves them). Files beside the anchor never mention the handbook.
- A named folder's `README.md`: what it is, how to start it, how to stop and clean up, what to check. Keep it short; the anchor carries the teaching.
- `requirements.txt` only for what the dev container lacks, or inside a project folder that teaches its own pinned environment (S02: `m4_fund_report/requirements.txt`); either way its pins match `courseware/.devcontainer/requirements.txt`.
- A config file whose lines each do a job (a Dockerfile, a pipeline YAML, a compose file) gets a plain line-by-line table in the anchor, in the file's own order: the line, then what it does in one short sentence.

## Walkthrough of an existing app (when the demo shows rather than builds)

Order: run it → see its shape → each part in turn → what it cost. Every part gets the same three beats: what it does · try it · how it works. Nothing named but unexplained, nothing explained but unnamed. Shared things introduced once on the simplest part.

## Offline fixtures for LLM demos

Recorded responses keyed by prompt hash, or a deterministic stub returning a valid Pydantic object, in `mN_fixtures/` or inside the module's named folder. The anchor runs with `LLM_MODE=fixture` by default and `LLM_MODE=live` when a key is present, and says which evidence each mode gives. Live behaviour is never claimed from a fixture run.
