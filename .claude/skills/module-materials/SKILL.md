# Module materials

Stage 7 of the seven. Turns the reviewed source into the artefact set MJB's sample module and artefact list will define. Definition of done: `reference/subtask-descriptions.md` → **Learner-facing materials ready**. The interim asset list is [references/asset-checklist.md](references/asset-checklist.md); replace it with MJB's when it arrives.

## Before you start

1. Read `programme-profile` (SKILL.md, `references/layout.md`) and this session's digest.
2. Confirm stage 6 is closed: the peer-review file has every must-fix resolved.
3. **Confirm the user has reviewed the content** (the overview, lesson plan, handbooks, demo and challenge as they now stand) and said to build. No PDF is built before that (user, 2026-10-15); a request to "make materials ready" without that review is answered with the checklist and the question.
4. Read `lesson-build` → Build and Ship state.

## Gates (a module does not ship past any of these)

- The user's review of the content, recorded in the session digest with the date, beside every user ruling of the build.
- The session checklist's part E (`module-builder/references/session-checklist.md`), in one command, `scripts/check-session.sh dayNN`: `module-audit` at 0 errors and 0 warnings (its formatting, handbook-numbering, Go deeper, handbook-mention and anchor checks included), `scripts/nbkit.py toc --check` for every notebook, `scripts/check_pins.py`, `scripts/test-dev-container.sh` and every service test passing; and the independent read-through's must-fixes applied (`module-review` → Session read-through).
- **No `<!-- sensitive: … -->` marker** (user, 2026-10-19): content follows `programme-profile` CG rule 2 (pros and cons, never limitations) the first time, and nothing waits for anyone to clear it. Any marker left is an audit error: list it, reword the passage to the rule, delete the marker and stop until it is fixed.
- **No CG-access notes** (user, 2026-10-16): no "Needs CG access" section, `::: blocked` callout or "the CG dev container" in anything, for programme review or delivery; the course runs on local containers (`programme-profile` rule 3). The audit warns on them and the build refuses a `::: blocked` callout.
- Demo anchor executed top to bottom and every folded solution rerun since the last edit.
- `challenge-solution/` rebuilt from the current challenge, executed with no error output and no `___` left, its task boxes and other markdown cells matching the challenge's (`module-challenge`). The audit warns on each of these; the `--reviewed` build stops on a missing `challenge-solution/` or file, a code cell that never ran, counts that don't run 1, 2, 3 in order, or files left untracked in a committed `challenge-solution/`, and every build stops on a notebook with no outputs or an error output.

## Assets

**The programme pages (user, 2026-11-02):** `unit00-programme/` ships `learner/start-here.pdf`, `programme-overview.pdf` and `setup.pdf`, `instructor/start-here.pdf`, `release-notes.pdf`, `delivery-guide.pdf` and `event-readiness.pdf`, the services' `INSTRUCTOR.pdf`, and the welcome day `day00-welcome/` built like a day (`day00_overview.pdf`, `day00_lesson_plan.docx`, `day00_slides.pptx` and `.pdf`); every build makes them, whatever the target.

**The rule (user, 2026-10-27): Drive gets everything in its final form.** Reading Markdown (overviews, handbooks, the lesson plan, start-here, release notes, each service's `INSTRUCTOR.md`, the release inventory) ships only as its PDF or Word file; working files that learners and instructors open or run (notebooks, project folders and their READMEs, data including `documents/*.md`, services, the dev container, files a demo opens) ship as they are; authoring files (`dayNN_anchors.md`, research packs) never ship.

1. **The session folder complete for the module**: its handbook, its lesson-plan block, its place in the overview, its demo and challenge sections and the files beside them (checklist).
2. **Figures and concept cards** accurate, one copy in `courseware/common/figures/<session>/`, each made by its script in `scripts/figures/dayNN/`; handbook figures captioned and eyeballed in the rendered PDF, demo cards and challenge recap visuals eyeballed in the anchors.
3. **Outputs, after the user's review**: `scripts/build-session.sh dayNN --reviewed` builds `release/latest/`, laid out exactly like `courseware/` (user, 2026-10-27): `.devcontainer/`; `common/` (`data/`, each `services/<name>/` a built session's overview names, `figures/<session>/`); `unit00-programme/learner/start-here.pdf` and `unit00-programme/instructor/` (`start-here.pdf`, `release-notes.pdf`, `services/<name>/INSTRUCTOR.pdf`); `RELEASE.pdf` (with `RELEASE.md` beside it for git and the checks, never synced); per session `learner/` (`module00-overview/dayNN_overview.pdf`; per module folder its handbook PDF, the challenge notebook and its project folder) and `instructor/` (`module00-overview/dayNN_lesson_plan.docx`, and the day's deck `dayNN_slides.pptx` with `dayNN_slides.pdf` beside it, built by `scripts/make_slides.py` from `dayNN_slides.md`, which never ships (user, 2026-10-27); per module folder the demo notebook and its files, `challenge-solution/`, and, in the module's `pdfs/` (user, 2026-10-27), the review PDFs `dayNN_mN_demo.pdf`, `dayNN_mN_challenge.pdf`, `dayNN_mN_challenge_solution.pdf` and a copy of the module's handbook PDF; module99 keeps its two in its folder). Every build, whatever its target, makes every `courseware/<unit>/<session>/` folder, so Drive shows every unit and session; a session not built yet is an empty folder (no `.gitkeep`). The full tree is in `programme-profile/references/layout.md` → Built outputs and sharing. Build into a scratch folder first (`--out <dir> --no-gates`) and look at it: each PDF's contents page (handbook sections numbered 1, 2, 3 … and 1.1, 1.2 … by the build, the Summary unnumbered), figures, captions and callouts; the Word timeline (`.venv/bin/python scripts/docx/preview_docx.py <docx> <dir>`); the deck's PDF, page by page (no text cut off, figures legible, nothing for learners' eyes only missing); the notebook PDFs' boxes, open solutions and appended files; the completed challenge's outputs and filled answer boxes; both `start-here.pdf` pages. Every gate must pass for the real build, among them no CG-access note and no `<!-- sensitive` marker in anything shipped (markers are retired, user, 2026-10-19), and no instructor material outside an `instructor/` folder (no lesson plan, demo, completed challenge, solutions-open PDF, release notes or `INSTRUCTOR.md` in `learner/` or `common/`). `release/latest/` is tracked in git, so a release is versioned when the user commits it; `releases/` is the builder's scratch and stays ignored.
4. **Nothing is zipped** (user, 2026-10-15): instructors receive `release/latest/`, laid out like `courseware/`, and nothing in it names `courseware/` or a `.md` that ships only as a PDF or Word file (the build renames those references to the shipped file and gates on it; user, 2026-10-19): shipped paths start from the course folder (`common/data/challenge/`, `common/services/remote-machine/`); learner text says "the course folder", never "the download" or "the zip". Learners don't get Drive (user, 2026-10-27). `courseware/unit00-programme/learner/start-here.md` (built to `release/latest/unit00-programme/learner/start-here.pdf`) tells learners what the course folder holds across every unit (u1 to u5), why the Dev Containers extension is required and how to open the folder with "Dev Containers: Reopen in Container", how to start a session's services (a general section; the remote machine is the example) and what to do at the start of each session; it never names Google Drive or any platform, and never mentions downloading or unzipping. Keep it true when the layout or setup changes.
5. **Slides only where the delivery approach needs them**: import reviewed content into Gamma, export to PowerPoint or Google Slides, adjust there (`decoded-slides` for layout and voice). Practical modules may need only welcome, navigation and wrap-up slides. Gamma never determines the curriculum.
6. **Setup notes**: the lesson plan's "Before the session" section (checklist, learner setup check) feeds the pair-specific setup checks and onboarding. What learners need from CG (laptops, Docker, accounts) goes in the IT prerequisites sheet (`designer/core/plan/cg-core-prerequisites.xlsx`) and Asana, never in the content. The timing overview is the lesson plan's "Session at a glance"; there is no separate timing file.

## Release on Google Drive (user, 2026-10-16; release/latest/ to Drive's release/latest/, 2026-10-27)

Drive holds one copy of the course folder, `release/latest/` in the shared drive's `Delivery & Workshop Materials/`, mirrored from `release/latest/` in final forms only (the sync leaves out `RELEASE.md`, the manifest, the lock and the stamp), for instructors (user, 2026-10-27). Learners don't get Drive. The Drive folders that held the release before (`courseware/`, then `ready-courseware/`) are retired by hand; the sync never touches them. Releases go per session, after the user's review. The full layout and the sharing rules are in `programme-profile/references/layout.md` → Built outputs and sharing.

Only the release owner releases (user, 2026-10-19): the build syncs only on the machine where the Drive folder is configured (`.sync-release.env`, or `CG_RELEASE_DRIVE` exported), skips the sync and says so anywhere else, and `--no-sync` skips it. Every developer installs `scripts/install-hooks.sh` once per clone; the sync hooks from `scripts/install-sync-release.sh` are the release owner's alone. The order is build (its gates, then `scripts/check_release.py`, then the sync) → confirm "verified" → commit `release/latest/`.

1. **Add a dated line to `courseware/unit00-programme/instructor/release-notes.md`**, newest first under its heading: the date, the session and what changed in one line, for example `- 2026-10-20 · S01 — first release: overview, Module 1 handbook, demo, challenge and its completed version.` Whoever releases writes it, before building and after the user's review.
2. **Build with `--reviewed`**: `scripts/build-session.sh dayNN --reviewed` (it runs the builder as `.venv/bin/python ./build-pdf`). Every gate passes, then the build writes `.build-manifest.json` at the top of `release/latest/` and runs `scripts/check_release.py` on it; only if that passes does it sync. The run also rebuilds the programme PDFs: `unit00-programme/learner/start-here.pdf` and `unit00-programme/instructor/start-here.pdf` and `release-notes.pdf`.
3. **Sync, replacing the previous copy.** On the release owner's machine this is automatic (user, 2026-10-19): the `--reviewed` build ends, after its release check, by running `scripts/sync-release.sh`, which mirrors `release/latest/` into `<CG_RELEASE_DRIVE>/release/latest/` (deletions included, inside that folder only, at most `CG_SYNC_MAX_DELETE` a run, 200 by default: check `scripts/sync-release.sh --dry-run` and raise it only when every deletion is expected; Drive's trash keeps them 30 days), and the git hooks from `scripts/install-sync-release.sh` sync again after every commit and whenever a pull, merge, checkout or rebase changes `release/latest/`. Every change must reach Drive (user, 2026-10-19): rebuild rather than edit the tree, never pass `--no-sync` unless the user asks, and confirm the sync ends with "verified: Drive matches release/latest/". A FAILED, abort or skip line goes to the user. The log is `~/Library/Logs/cg-core-sync-release.log`. By hand, the rule is the same: delete the old folder before putting the new one in its place (copying over it keeps files the build dropped, and a browser upload of a folder with the same name adds a second copy beside it); Drive for desktop is the easier way.
4. **Confirm the release check, then commit `release/latest/`**: the build's `scripts/check_release.py` run must end "check_release: passed" (rerun it by hand with `.venv/bin/python scripts/check_release.py` before committing if anything changed since). It checks every file in `release/latest/` against the `.build-manifest.json` the build wrote at its top (tracked, never synced to Drive), so any hand edit, extra or missing file fails, and the release's shape (instructor material only under `instructor/` folders, no `dayNN_anchors.md`, no repo folder names, markers, CG-access notes or absolute paths, challenges cleared and demos and completed challenges executed, every unit and session folder, references named as they ship, house covers, no command split from its output). A warning that `courseware/` changed since the build means the release is behind the source: report it. Never fix a failure by editing the tree or the manifest: fix `courseware/` and rebuild. The pre-commit hook from `scripts/install-hooks.sh` (every clone installs it once) checks the staged tree again and refuses a commit that doesn't match; commit only when the user asks.
5. **Check `release/latest/.devcontainer/` survived on Drive**, with `devcontainer.json` in it: browser folder uploads can drop hidden folders, and Drive for desktop keeps them. Without it, the course folder won't reopen in the dev container.
6. **Tell people what changed**: send instructors the release-notes line and the folder link.

## Rules

- No duplicate, changing content in Google Docs during development.
- Learner instructions stay flexible for live adaptation.
- Everything in the repository; nothing only on a laptop or in Gamma.

## Submit

Write `designer/reviews/dayNN-submission.md` (or append the module to it): what is included, the working-title caveat, the date of the user's review, the PDF paths and manifest hashes. Tell the user the one-line Asana status. Record the submission date in the session digest.

**Slides follow the plan (user, 2026-10-27).** Before any build, if the lesson plan changed since the deck was last synced: `.venv/bin/python scripts/make_slides.py sync dayNN`, then `check dayNN`. Every deck has the standard Setup check slide straight after Meet and greet (the same in every unit and day: "Check your setup before we start.", the shared picture `common/figures/shared/setup-check.png` from `scripts/figures/shared_setup_check.py`, a walk-the-room cue in the notes; a slide only, no lesson-plan row). Thank you for participating shows only its title and photo: the feedback form is the instructor's note, never on a slide. Each module's WHAT, WHY AND HOW is a question statement slide, then three `recap-3` tiles of the anchors file's short phrases. Slide text is concise (titles of 8 words or fewer, at most 3 bullets of 12 words or fewer, the rest in the notes); `check` fails on longer text. The audit runs the same check, so `scripts/check-session.sh dayNN` fails on a deck out of step with the plan; run it before the build.

**Slide look (user, 2026-10-27).** Decks use the builder's own Decoded master, as Fundamentals' do. The 2026 Decoded Slide Templates & Library look (reference/, git-ignored) is requested from Decoded's builder owners as a master; switch the pinned builder when it lands, with no change to the slide sources. The slide PDF builds in Docker (`tools/slides-pdf/`), so a release needs Docker Desktop running.

**Release details (user, 2026-11-02).**
- `RELEASE.md` and `RELEASE.pdf` list only each released unit folder and day folder with its number of files; `check_release.py` recomputes the counts. The source commit is in `.last-build`.
- Programme pages of four pages or more (programme-overview, setup, delivery-guide, event-readiness) get the house contents page, like the day overviews and handbooks; start-here and the release notes don't.
- The two overviews also go to Drive as Word files, beside `release/`: `internal-programme-overview.docx` and the shareable `cg-core-programme-overview.docx`, both from `scripts/docx/build_overview.js` (the second with the label "Programme overview"). Build them into `review/` first; copy them to the pinned folder only with a confirmed release, and check they match.

**Word builder options (2026-11-04).** `scripts/docx/build_overview.js` builds any Markdown note in the house style: `--landscape` for A4 landscape, `--subtitle "…"` for the line under the title, mermaid code blocks drawn to pictures with the Mermaid CLI in `scripts/mermaid/`, `[text](url)` links, `<br>` for lines inside a table cell (bullet lines as "• …", sub-bullets as no-break spaces plus "◦ …"), and "  - " for nested list items. Internal notes go to `review/` first, then to the pinned Drive folder beside the overviews, and get committed only when the user says so.

**One-pagers (2026-11-04).** `build_overview.js --landscape --compact` makes a client-facing one-pager: 1 cm margins, the title and subtitle beside a small logo, 7-point table type, tight cell spacing, no spacer after a table and a hidden one-point final paragraph so Word adds no blank page; `--widths 15,30,55` sets column shares, `--small 13` drops the table type to 6.5 points if it still spills. Check the page count with `scripts/docx/preview_docx.py`, which now loads the house fonts so wrapping matches Word; a second page carrying only the footer means the trailing paragraph, not content.
